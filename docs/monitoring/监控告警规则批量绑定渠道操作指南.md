# 监控告警规则 — 批量绑定通知渠道操作指南

> 本文档详细介绍如何通过平台前端 UI 和 API 接口，对已创建的告警规则**批量绑定、追加或移除**通知渠道，  
> 无需逐条修改，支持按分组/级别/关键字等条件筛选匹配。

---

## 一、功能概述

### 1.1 解决的问题

| 场景 | 传统做法 | 新功能 |
|------|---------|--------|
| 新增了钉钉群，50 条规则都要绑上 | 逐条编辑规则设置通知渠道 | 一次性按条件匹配 + 追加渠道 |
| 运维换群，需要替换旧渠道 | 逐条编辑逐条改 | 一次性替换所有匹配规则的渠道 |
| 某个渠道下线要摘除 | 逐条找哪些绑了该渠道 | 一次性批量移除指定渠道 |
| 导入 YAML 后忘记绑渠道 | 再一条条补 | 按组批量绑定 |

### 1.2 支持的绑定模式

| 模式 | 英文 | 说明 |
|------|------|------|
| **替换** | `replace` | 清除旧渠道，统一设为所选渠道 |
| **追加** | `append` | 保留原有渠道，追加新渠道（自动去重） |
| **移除** | `remove` | 从匹配规则中移除指定渠道 |

### 1.3 支持的匹配条件

| 条件 | 字段 | 匹配方式 | 示例 |
|------|------|---------|------|
| 分组 | `group` | 精确匹配 | `infrastructure`、`kubernetes` |
| 级别 | `severity` | 精确匹配 | `critical`、`warning`、`info` |
| 名称关键字 | `keyword` | 模糊匹配 (LIKE) | `CPU`、`Pod`、`磁盘` |
| 数据源 | `datasource_id` | 精确匹配 | `1` |
| 全选 | `match_all` | 所有启用的规则 | `true` |

> 多个条件同时生效时为 **AND** 逻辑（同时满足）。

## 二、前端操作步骤（UI 方式）

### 2.1 入口位置

进入 **监控 → 告警规则** 页面，顶部操作栏有 **「批量绑定渠道」** 按钮（绿色边框按钮）。

```
┌─────────────────────────────────────────────────────────────┐
│  告警规则                                                     │
│  配置基于 PromQL 的告警规则，支持多级别通知                       │
│                                                               │
│  [🔔 批量绑定渠道]  [⬆ 导入]  [⬇ 导出]  [+ 新增规则]           │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 操作流程

点击按钮后弹出操作面板，分三步完成：

#### Step 1: 设置匹配条件

| 控件 | 说明 |
|------|------|
| 按分组 | 下拉选择已有分组（如 `infrastructure`、`kubernetes`） |
| 按级别 | 选择 `Critical` / `Warning` / `Info` |
| 按名称关键字 | 输入文本，模糊匹配规则名称 |
| 所有启用的规则 | 勾选后忽略上方条件，匹配全部启用规则 |

> **留空 = 不限制该条件。** 例如只选分组不选级别，则该分组下所有级别的规则都会被匹配。

#### Step 2: 选择通知渠道

展示所有已启用的通知渠道卡片（类型图标 + 名称），**可多选**。

支持的渠道类型：
- 🔷 钉钉 (DingTalk)
- 🟦 飞书 (Feishu)
- 🟩 企业微信 (WeChat Work)
- 🔗 Webhook
- 📧 邮件 (Email)

> 如果没有显示任何渠道，请先到 **通知渠道管理** 页面创建并启用渠道。

#### Step 3: 选择绑定模式

三种模式以卡片形式展示，点击选中：

| 卡片 | 效果说明 |
|------|---------|
| **替换** | 匹配到的规则渠道字段被直接覆盖为所选渠道 |
| **追加** | 在原有渠道基础上追加（自动去重，不会重复绑定） |
| **移除** | 从匹配规则的已绑定渠道中移除所选渠道 |

#### Step 4: 确认执行

点击 **「确认执行」** 按钮，系统会返回操作结果：

```
📊 操作结果
   匹配 25 条  |  成功 25  |  失败 0
   筛选条件: group=infrastructure AND severity=warning
```

## 三、API 接口方式

### 3.1 接口信息

```
POST /api/v1/monitoring/alert-rule/batch-bind-channels
Content-Type: application/json
```

### 3.2 请求参数

```json
{
  "rule_ids": [],              // 方式1: 精确指定规则ID (优先级最高)
  "group": "infrastructure",   // 方式2: 按分组匹配
  "severity": "warning",       // 按级别匹配
  "keyword": "",               // 按名称模糊匹配
  "datasource_id": 0,          // 按数据源匹配
  "match_all": false,          // 是否匹配全部启用规则

  "notify_channels": "1,3",    // 必填：目标渠道ID (逗号分隔)
  "mode": "append"             // 绑定模式: replace/append/remove
}
```

**两种使用方式：**

| 方式 | 说明 |
|------|------|
| `rule_ids` 非空 | 忽略所有筛选条件，直接按 ID 列表操作 |
| `rule_ids` 为空 | 使用 group/severity/keyword/datasource_id/match_all 条件匹配 |

### 3.3 响应格式

```json
{
  "code": 0,
  "msg": "批量操作完成: 成功25 失败0",
  "data": {
    "total": 25,
    "success": 25,
    "failed": 0,
    "matched": 25,
    "filter": "group=infrastructure AND severity=warning"
  }
}
```

### 3.4 安全限制

- 单次最多操作 **500 条** 规则
- 条件为空且未设 `match_all` 时返回错误提示
- 仅操作 `enabled=1 AND is_del=0` 的规则

## 四、常用操作场景示例

### 场景 1：新钉钉群全量接入

刚创建了一个新的钉钉告警群（渠道 ID=3），要让所有规则都发到这个群：

```json
{
  "match_all": true,
  "notify_channels": "3",
  "mode": "append"
}
```

### 场景 2：按分组指定不同渠道

`infrastructure` 组发运维群，`application` 组发开发群：

```bash
# 运维群
curl -X POST http://localhost:8080/api/v1/monitoring/alert-rule/batch-bind-channels \
  -H "Content-Type: application/json" \
  -d '{"group":"infrastructure", "notify_channels":"1", "mode":"replace"}'

# 开发群
curl -X POST http://localhost:8080/api/v1/monitoring/alert-rule/batch-bind-channels \
  -H "Content-Type: application/json" \
  -d '{"group":"application", "notify_channels":"2", "mode":"replace"}'
```

### 场景 3：Critical 级别追加飞书通知

所有 Critical 级别的告警额外追加飞书渠道（ID=5）：

```json
{
  "severity": "critical",
  "notify_channels": "5",
  "mode": "append"
}
```

### 场景 4：移除已下线的旧渠道

渠道 ID=2 已经不用了，从所有规则中移除：

```json
{
  "match_all": true,
  "notify_channels": "2",
  "mode": "remove"
}
```

### 场景 5：组合条件 — kubernetes 组中含 "Pod" 的 warning 规则

```json
{
  "group": "kubernetes",
  "severity": "warning",
  "keyword": "Pod",
  "notify_channels": "1,3",
  "mode": "replace"
}
```

### 场景 6：按 ID 精确绑定（适合自动化脚本）

```json
{
  "rule_ids": [1, 5, 8, 12, 15],
  "notify_channels": "1,2",
  "mode": "replace"
}
```

## 五、配合 YAML 导入使用

### 5.1 导入时直接指定渠道（推荐）

YAML 批量导入时可以同时指定渠道，无需导入后再批量绑定：

```json
POST /api/v1/monitoring/alert-rule/import-yaml
{
  "yaml": "groups:\n  - name: infrastructure\n    rules: ...",
  "datasource_id": 1,
  "overwrite": true,
  "default_notify_channels": "1",
  "group_channels": {
    "infrastructure": "1,2",
    "kubernetes": "3",
    "application": "2,3"
  },
  "auto_route": false
}
```

### 5.2 渠道决策优先级（4 级）

导入时渠道的决定逻辑从高到低：

```
1️⃣ 规则自身 annotations.notify_channels   ← 最高优先级（YAML 中直接写）
2️⃣ group_channels[当前组名]                ← 按组映射
3️⃣ default_notify_channels                ← 全局默认
4️⃣ auto_route（路由策略匹配）              ← 最低优先级
```

### 5.3 YAML 中为单条规则指定渠道

```yaml
groups:
  - name: infrastructure
    rules:
      - alert: NodeCPUHigh
        expr: '...'
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "CPU 使用率过高"
          notify_channels: "1,3"    # ← 这条规则走渠道 1 和 3
```

### 5.4 先导入后批量绑定（两步走）

如果导入时忘了指定渠道，导入完成后可以：

```bash
# Step 1: 导入 YAML（不指定渠道）
curl -X POST .../import-yaml -d '{"yaml":"...", "datasource_id":1}'

# Step 2: 对导入的组批量绑定渠道
curl -X POST .../batch-bind-channels \
  -d '{"group":"infrastructure", "notify_channels":"1,2", "mode":"replace"}'
```

## 六、PowerShell 脚本示例

```powershell
# ===== 批量绑定通知渠道 PowerShell 脚本 =====

$baseUrl = "http://localhost:8080/api/v1/monitoring/alert-rule/batch-bind-channels"
$headers = @{ "Content-Type" = "application/json"; "Cookie" = "session=YOUR_TOKEN" }

# 场景：按分组绑定不同渠道
$bindings = @(
  @{ group = "infrastructure"; notify_channels = "1,2"; mode = "replace" },
  @{ group = "kubernetes";     notify_channels = "1,3"; mode = "replace" },
  @{ group = "application";    notify_channels = "2,3"; mode = "replace" }
)

foreach ($b in $bindings) {
  $body = $b | ConvertTo-Json
  $resp = Invoke-RestMethod -Uri $baseUrl -Method POST -Body $body -Headers $headers
  Write-Host "✅ [$($b.group)] 成功: $($resp.data.success) / 匹配: $($resp.data.matched)"
}
```

## 七、注意事项与最佳实践

### 7.1 操作前检查清单

| 检查项 | 说明 |
|--------|------|
| 渠道已启用 | 确认目标渠道在「通知渠道」页面状态为启用 |
| 渠道已测试 | 建议先通过「测试」按钮验证渠道 webhook 可达 |
| 条件正确 | 批量操作前建议先在列表页用筛选栏确认规则范围 |
| 规则已启用 | 批量绑定仅对 `enabled=true` 的规则生效 |

### 7.2 操作安全

- **单次上限 500 条**：超出时系统拒绝并返回匹配数量
- **追加模式去重**：不会重复绑定同一渠道
- **条件为空保护**：未设条件也未勾选 `match_all` 时无法执行
- **仅影响启用规则**：已禁用/已删除的规则不受影响

### 7.3 推荐工作流

```
创建通知渠道 → 测试验证 → 批量导入/创建告警规则 → 按组批量绑定渠道
                                                    ↓
                                          后续新增渠道用「追加」模式
                                          渠道下线用「移除」模式
```

### 7.4 与路由策略的关系

| 机制 | 适用场景 | 特点 |
|------|---------|------|
| 批量绑定渠道 | 手动管理，精确控制 | 结果直接写入规则的 notify_channels 字段 |
| 路由策略 | 自动化分发 | 运行时动态匹配，适合新增规则时自动路由 |
| 兜底策略 | 兜底保障 | 当没有任何匹配时，走 IsDefault=true 的默认渠道 |

> 建议：少量规则用批量绑定精确控制，大量且持续新增的规则用路由策略自动匹配。

## 九、故障排查

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 操作后渠道没生效 | 规则 notify_channels 正确但通知渠道本身未启用 | 到渠道管理页面启用对应渠道 |
| 匹配 0 条规则 | 条件组合太严格 / 规则未启用 | 放宽条件或检查规则状态 |
| 超过 500 条限制 | 匹配范围太大 | 缩小筛选范围分批操作 |
| 追加后出现重复通知 | 通知渠道配置了相同 webhook | 检查渠道配置去重 |
| 前端看不到渠道卡片 | 所有渠道都处于禁用状态 | 启用至少一个渠道 |
