### 1.2 P0 缺陷：StatefulSet/DaemonSet 滚动更新未等待完成

#### 问题描述

在 `cicd_pipeline.go` 的 `executeAutoDeployAsync` 函数中，`switch workloadKind` 分支存在逻辑缺陷：

```go
// 修复前（有 Bug）
case "Deployment":
    _, err = kubeClient.AppsV1().Deployments(...).Patch(...)
    if err == nil {
        rolloutResult, err = s.waitAutoDeployRollout(...)  // ✅ 等待
    }
case "StatefulSet":
    _, err = kubeClient.AppsV1().StatefulSets(...).Patch(...)
    // ❌ 没有等待 Rollout，直接标记成功
case "DaemonSet":
    _, err = kubeClient.AppsV1().DaemonSets(...).Patch(...)
    // ❌ 同样没有等待
```

#### 影响范围

- **触发条件**: 所有使用 StatefulSet 或 DaemonSet 作为部署目标的 CI/CD 流水线
- **现象**: 平台显示"部署成功"，但实际只有一个 Pod 被更新（高序号 Pod），其余 Pod 仍运行旧镜像
- **根因**: StatefulSet 默认滚动更新策略是从高序号到低序号逐个替换 Pod（如 2 副本：先 pod-1，再 pod-0）。Patch API 返回后 K8s 控制器才开始滚动更新，平台未等待即返回

#### 修复方案

新增两个函数，严格检查 Rollout 完成条件：

| 函数 | 完成条件 | 参考 |
|------|---------|------|
| `waitAutoDeployStatefulSetRollout` | UpdatedReplicas==replicas && CurrentReplicas==UpdatedReplicas && ReadyReplicas==replicas | `kubectl rollout status sts` |
| `waitAutoDeployDaemonSetRollout` | UpdatedNumberScheduled==DesiredNumberScheduled && NumberReady==DesiredNumberScheduled | `kubectl rollout status ds` |

两个函数均包含：
- 5 分钟超时 + 5 秒轮询间隔
- Pod 级别错误检测（ImagePullBackOff / CrashLoopBackOff）
- 每轮输出详细日志（期望/更新/就绪/Generation）

#### 评审结论

### 1.3 Feature: Go Pipeline 模板通用化

#### 新增参数

| 参数 | 类型 | 默认值 | 用途 |
|------|------|--------|------|
| `EXTRA_REPOS` | string | 空 | 预克隆私有依赖仓库（格式: `url\|path;url\|path`） |
| `BINARY_NAME` | string | 空 | 自定义二进制名称（空=自动从 go.mod module 推断） |
| `USE_PROJECT_DOCKERFILE` | bool | false | 优先使用项目自带 Dockerfile |

#### 新增构建阶段

`Clone Extra Repos` — 在 Dependencies 阶段之前执行：
- 解析 `EXTRA_REPOS` 参数（`;` 分隔多个仓库）
- 自动注入 `GIT_CREDENTIAL_ID` 凭证到 HTTPS clone URL
- `git clone --depth 1` 浅克隆到指定相对路径

#### 评审结论

| 项 | 结论 |
|----|------|
| 凭证安全 | ✅ 使用 `withCredentials` 注入，不暴露明文 |
| 路径校验 | ✅ Dependencies 阶段增加 replace 路径存在性检查 |
| 向后兼容 | ✅ 参数默认空/false，不影响现有 Go 项目 |
| 后端注入 | ✅ `injectLanguageParams` 已注入默认值 |
| 前端兼容 | ✅ 复用现有 env_vars 机制，无需改前端 |

### 1.4 Optimization: Maven 构建资源配置缩减

| 配置项 | 修改前 | 修改后 | 原因 |
|--------|--------|--------|------|
| CPU Request | 1 | 500m | 原配置过大，导致集群资源浪费 |
| CPU Limit | 4 | 2 | 多数项目不需要 4 核 |
| Memory Request | 2Gi | 1Gi | 合理配置 |
| Memory Limit | 8Gi | 4Gi | 原配置过高 |
| MAVEN_OPTS Xmx | 4096m | 1024m | 与 Memory Limit 匹配 |

### 3.2 CI/CD 流水线数据流

```
用户创建流水线 → 前端 env_vars → 后端 injectLanguageParams
    → Jenkins buildWithParameters → K8s Pod Agent 启动
    → Clone Code → Clone Extra Repos (Go) → Dependencies
    → Compile → Test → SonarQube → Build & Push Image
    → Jenkins 回调平台 → HMAC 验证
    → autoDeploy: Patch Image → waitRollout (所有 Pod Ready)
    → 飞书/钉钉通知 → 更新流水线状态
```

### 4.2 上线步骤

#### 第一阶段：代码提交与构建

```
1. git add → commit → push origin main → push gitlab main
2. 双远程仓库 main 分支一致性验证
3. 后端镜像构建并推送到镜像仓库
   镜像 tag: v1.2.0
4. Jenkins 模板同步（Pipeline script from SCM 自动拉取）
```

#### 第二阶段：后端部署

```
1. kubectl set image deployment/k8soperation \
     k8soperation=<registry>/k8soperation:v1.2.0 -n devops
2. kubectl rollout status deployment/k8soperation -n devops
3. 验证服务健康: curl /api/v1/health
4. 验证 CI/CD 接口: POST /api/v1/cicd/pipeline/list
```

#### 第三阶段：功能验证

| 验证项 | 方法 | 预期结果 |
|--------|------|---------|
| StatefulSet Rollout | 创建 StatefulSet 类型流水线并触发构建 | 所有 Pod 更新完毕后才报成功 |
| DaemonSet Rollout | 创建 DaemonSet 类型流水线并触发构建 | 所有节点 Pod 更新完毕后才报成功 |
| Go 私有依赖 | 创建 Go 流水线，配置 EXTRA_REPOS | 依赖仓库自动克隆，编译成功 |
| Go 自动检测 | 不填 BUILD_DIR，验证 go.mod module 推断 | 二进制名正确 |
| Java 多模块 | 不填 BUILD_DIR，验证自动检测 | 正确找到 spring-boot 模块 |
| Maven 构建 | 触发 Java 流水线 | 资源使用在 500m/1Gi ~ 2/4Gi 范围内 |

#### 第四阶段：灰度验证

```
1. 选择 1 个 StatefulSet 项目进行发布验证
2. 确认所有副本都更新到新镜像
3. 确认平台日志中看到 [ROLLOUT-STS] 轮询输出
4. 确认通知消息中包含正确的 Rollout 结果
```

#### 第五阶段：全量上线

```
1. 确认灰度验证通过
2. 更新流水线模板（Jenkins Job 重新加载 SCM）
3. 通知团队新版本已上线
4. 更新平台版本号 → v1.2.0
```

### 4.3 回滚方案

| 场景 | 回滚操作 |
|------|---------|
| 后端服务异常 | `kubectl rollout undo deployment/k8soperation -n devops` |
| Maven 资源不足 | 修改 `java-spring-pipeline.groovy` 恢复原配置，Jenkins 重新加载 SCM |
| Go 模板异常 | 参数默认空/false，不影响现有 Go 项目；如需彻底回滚，`git revert` 后重新加载 SCM |
| StatefulSet Rollout 修复异常 | `git revert` + 重新构建镜像 + 重新部署 |
