## 二、现有单体架构分析

### 2.1 当前模块划分

```
k8soperation (单体进程)
├── Auth & User        → 认证登录、JWT、Session、用户管理
├── RBAC              → 三域六角色权限体系
├── K8s Cluster       → 集群元数据 CRUD（DB层）
├── K8s Resources     → 16+ 种 K8s 资源操作（Pod/Deploy/STS/DS/Job/CronJob...）
├── CI/CD             → 流水线、构建、发布、制品库、通知、模板
├── Monitoring        → Prometheus集成、告警规则、通知渠道、静默
├── AI Assistant      → OpenAI Function Calling、高危审批
├── AIOps             → 智能巡检、AI分析
├── App Store         → 应用商城、Helm/YAML安装
├── Image Registry    → 镜像仓库管理、ACR/Harbor
├── Platform          → 健康检查、系统设置、审计日志
└── Workers           → CICD Worker、Alert Eval、Audit Cleanup、AIOps Inspection
```

### 2.2 当前痛点

| 痛点 | 描述 |
|------|------|
| 模块耦合 | 所有模块共享同一进程，CI/CD 构建故障可能影响监控告警 |
| 弹性不足 | 无法按模块独立扩缩容，AI/CICD 是计算密集型，资源管理是 IO 密集型 |
| 迭代冲突 | 监控模块频繁迭代会阻塞 CICD 发布 |
| 单点故障 | 一个 panic 导致全平台不可用 |
| 技术锁定 | 无法为不同模块选择最优技术方案 |

### 2.3 模块间依赖关系

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
```

## 三、微服务拆分方案

### 3.1 拆分原则

1. **业务边界清晰**：按领域驱动设计（DDD）的限界上下文拆分
2. **数据独立**：每个服务拥有独立的数据库 Schema（逻辑隔离，物理可共享）
3. **高内聚低耦合**：服务间通过 gRPC/事件总线通信，禁止直接访问他方数据库
4. **渐进式演进**：支持从单体逐步拆出，非一步到位

### 3.2 微服务拆分清单

| 序号 | 服务名 | 职责 | 独立 DB Schema | 通信方式 |
|------|--------|------|----------------|----------|
| 1 | `gateway-svc` | API 网关、路由、限流、认证透传 | 无 | HTTP/WebSocket → gRPC |
| 2 | `auth-svc` | 登录认证、JWT签发/刷新、Session、用户CRUD | `auth_db` | gRPC |
| 3 | `rbac-svc` | 角色、权限、资源绑定、鉴权判定 | `rbac_db` | gRPC |
| 4 | `cluster-svc` | 集群元数据CRUD、连接池管理、多集群路由 | `cluster_db` | gRPC |
| 5 | `resource-svc` | K8s 全资源操作（Pod/Deploy/STS等16+种） | 无（直连 K8s API） | gRPC + WebSocket |
| 6 | `cicd-svc` | 流水线、构建、发布、制品、Jenkins集成 | `cicd_db` | gRPC + NATS |
| 7 | `monitor-svc` | 告警规则、通知渠道、静默、数据源管理 | `monitor_db` | gRPC + NATS |
| 8 | `ai-svc` | AI 对话、Function Calling、AIOps巡检 | `ai_db` | gRPC + NATS |
| 9 | `appstore-svc` | 应用商城、Helm/YAML安装、版本管理 | `appstore_db` | gRPC |
| 10 | `image-svc` | 镜像仓库、清理策略、ACR/Harbor对接 | `image_db` | gRPC |
| 11 | `platform-svc` | 系统设置、审计日志、健康检查聚合 | `platform_db` | gRPC + NATS |
| 12 | `notify-svc` | 统一通知（钉钉/飞书/邮件/Webhook） | `notify_db` | NATS（纯消费） |

## 四、服务注册与发现

### 4.1 技术选型对比

| 方案 | 一致性模型 | 健康检查 | K8s 集成 | Go 生态 | 推荐场景 |
|------|-----------|----------|----------|---------|----------|
| **Consul** | CP+AP 可选 | TCP/HTTP/gRPC | 原生支持 | 成熟 | 混合云、多机房 |
| etcd | 强一致(CP) | 需自实现 | K8s 自带 | 成熟 | 已有 etcd 集群 |
| Nacos | AP/CP 可切换 | 内置 | 需适配 | Java 为主 | Java 生态 |
| K8s Service | DNS 发现 | 探针 | 原生 | 原生 | 纯 K8s 部署 |

**推荐方案：Consul + K8s Service 双模式**

- **K8s 内部**：利用 K8s Service + DNS 做服务发现（零成本）
- **跨集群/混合部署**：Consul 做跨机房服务注册发现
- **本地开发**：Consul Agent dev 模式

### 4.3 服务注册流程

```go
// pkg/registry/consul.go

package registry

import (
    "fmt"
    "github.com/hashicorp/consul/api"
)

type ServiceRegistry struct {
    client *api.Client
    svcID  string
}

type ServiceConfig struct {
    Name    string   // 服务名，如 "auth-svc"
    ID      string   // 实例 ID，如 "auth-svc-node1-50051"
    Address string   // 服务地址
    Port    int      // gRPC 端口
    Tags    []string // 标签，如 ["grpc", "v1"]
    Meta    map[string]string // 元数据
}

func NewServiceRegistry(consulAddr string) (*ServiceRegistry, error) {
    config := api.DefaultConfig()
    config.Address = consulAddr
    client, err := api.NewClient(config)
    if err != nil {
        return nil, fmt.Errorf("consul client init failed: %w", err)
    }
    return &ServiceRegistry{client: client}, nil
}

// Register 注册服务到 Consul
func (r *ServiceRegistry) Register(cfg ServiceConfig) error {
    reg := &api.AgentServiceRegistration{
        ID:      cfg.ID,
        Name:    cfg.Name,
        Address: cfg.Address,
        Port:    cfg.Port,
        Tags:    cfg.Tags,
        Meta:    cfg.Meta,
        Check: &api.AgentServiceCheck{
            GRPC:                           fmt.Sprintf("%s:%d", cfg.Address, cfg.Port),
            Interval:                       "10s",
            Timeout:                        "3s",
            DeregisterCriticalServiceAfter: "30s",
        },
    }
    r.svcID = cfg.ID
    return r.client.Agent().ServiceRegister(reg)
}

// Deregister 服务下线
func (r *ServiceRegistry) Deregister() error {
    if r.svcID == "" {
        return nil
    }
    return r.client.Agent().ServiceDeregister(r.svcID)
}
```

### 4.4 服务发现与负载均衡

```go
// pkg/discovery/resolver.go

package discovery

import (
    "fmt"
    "sync"
    "github.com/hashicorp/consul/api"
    "google.golang.org/grpc/resolver"
)

const scheme = "consul"

type consulResolverBuilder struct {
    client *api.Client
}

func NewConsulResolverBuilder(consulAddr string) (resolver.Builder, error) {
    config := api.DefaultConfig()
    config.Address = consulAddr
    client, err := api.NewClient(config)
    if err != nil {
        return nil, err
    }
    return &consulResolverBuilder{client: client}, nil
}

func (b *consulResolverBuilder) Build(target resolver.Target, cc resolver.ClientConn, opts resolver.BuildOptions) (resolver.Resolver, error) {
    r := &consulResolver{
        client:      b.client,
        serviceName: target.Endpoint(),
        cc:          cc,
        done:        make(chan struct{}),
    }
    go r.watch()
    return r, nil
}

func (b *consulResolverBuilder) Scheme() string { return scheme }

type consulResolver struct {
    client      *api.Client
    serviceName string
    cc          resolver.ClientConn
    done        chan struct{}
    mu          sync.Mutex
}

func (r *consulResolver) watch() {
    var lastIndex uint64
    for {
        select {
        case <-r.done:
            return
        default:
        }
        services, meta, err := r.client.Health().Service(r.serviceName, "", true, &api.QueryOptions{
            WaitIndex: lastIndex,
            WaitTime:  0, // 长轮询
        })
        if err != nil {
            continue
        }
        lastIndex = meta.LastIndex

        var addrs []resolver.Address
        for _, svc := range services {
            addr := fmt.Sprintf("%s:%d", svc.Service.Address, svc.Service.Port)
            addrs = append(addrs, resolver.Address{Addr: addr})
        }
        r.cc.UpdateState(resolver.State{Addresses: addrs})
    }
}

func (r *consulResolver) ResolveNow(opts resolver.ResolveNowOptions) {}
func (r *consulResolver) Close() { close(r.done) }
```

### 4.5 gRPC 客户端调用示例

```go
// 服务间调用 auth-svc 的示例
package main

import (
    "google.golang.org/grpc"
    "google.golang.org/grpc/balancer/roundrobin"
    pb "k8soperation/proto/auth"
)

func NewAuthClient(consulAddr string) (pb.AuthServiceClient, error) {
    // 注册 Consul Resolver
    builder, _ := discovery.NewConsulResolverBuilder(consulAddr)
    resolver.Register(builder)

    // 建立连接（自动从 Consul 发现 auth-svc 实例）
    conn, err := grpc.Dial(
        "consul:///auth-svc",
        grpc.WithInsecure(),
        grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`),
    )
    if err != nil {
        return nil, err
    }
    return pb.NewAuthServiceClient(conn), nil
}
```

### 4.7 双模发现策略

```go
// pkg/discovery/factory.go

package discovery

import "os"

type DiscoveryMode string

const (
    ModeConsul DiscoveryMode = "consul"
    ModeK8s    DiscoveryMode = "k8s"
)

// AutoDetect 自动检测运行环境
func AutoDetect() DiscoveryMode {
    // 在 K8s Pod 中会存在此环境变量
    if os.Getenv("KUBERNETES_SERVICE_HOST") != "" {
        return ModeK8s
    }
    return ModeConsul
}

// GetServiceAddr 根据发现模式返回目标服务地址
func GetServiceAddr(serviceName string, mode DiscoveryMode) string {
    switch mode {
    case ModeK8s:
        // K8s DNS 直连
        return serviceName + ".k8s-platform.svc.cluster.local:50051"
    case ModeConsul:
        // Consul Resolver 格式
        return "consul:///" + serviceName
    default:
        return serviceName + ":50051"
    }
}
```

### 9.2 gRPC 拦截器（统一中间件）

```go
// pkg/middleware/grpc_interceptor.go

package middleware

import (
    "context"
    "time"
    "go.uber.org/zap"
    "google.golang.org/grpc"
    "go.opentelemetry.io/otel"
)

// UnaryServerInterceptor 统一 gRPC 一元拦截器
func UnaryServerInterceptor(logger *zap.Logger) grpc.UnaryServerInterceptor {
    return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
        start := time.Now()

        // 链路追踪
        tracer := otel.Tracer("grpc-server")
        ctx, span := tracer.Start(ctx, info.FullMethod)
        defer span.End()

        // 执行请求
        resp, err := handler(ctx, req)

        // 日志记录
        duration := time.Since(start)
        logger.Info("gRPC call",
            zap.String("method", info.FullMethod),
            zap.Duration("duration", duration),
            zap.Error(err),
        )

        return resp, err
    }
}
```

### 10.1 熔断降级（Circuit Breaker）

```go
// pkg/circuitbreaker/breaker.go

package circuitbreaker

import (
    "time"
    "github.com/sony/gobreaker"
)

func NewCircuitBreaker(name string) *gobreaker.CircuitBreaker {
    settings := gobreaker.Settings{
        Name:        name,
        MaxRequests: 3,                    // 半开状态允许通过的请求数
        Interval:    60 * time.Second,     // 统计窗口
        Timeout:     30 * time.Second,     // 熔断持续时间
        ReadyToTrip: func(counts gobreaker.Counts) bool {
            failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
            return counts.Requests >= 10 && failureRatio >= 0.6 // 失败率≥60%触发熔断
        },
    }
    return gobreaker.NewCircuitBreaker(settings)
}
```

## 十六、Vue 前端微服务化适配方案

### 16.6 BFF（Backend For Frontend）层职责

BFF 不是必须的，但以下场景强烈推荐引入：

| 场景 | 没有 BFF | 有 BFF |
|------|---------|--------|
| 一次页面渲染需调 5 个服务 | 前端发 5 次请求，瀑布流慢 | BFF 并发聚合，1 次返回 |
| 不同端字段需求不同（PC/移动） | 后端按最大字段返回 | BFF 按端裁剪 |
| 跨服务字段拼装（用户名 + 集群名 + 应用名） | 前端遍历多次查询 | BFF 批量 IN 查询 |
| WebSocket 多路推送 | 每个服务一个连接 | BFF 单连接多路复用 |
| 灰度版本切换 | 前端硬编码 URL | BFF 动态路由 |

**BFF 推荐技术栈**：Go + Gin（与后端栈一致）或 Node.js + Nest.js（前端团队友好）。

```go
// services/bff/internal/handler/dashboard.go
// 仪表盘聚合接口示例：一次返回集群、Pod、告警、流水线四种数据
func (h *DashboardHandler) GetOverview(c *gin.Context) {
    var (
        clusters  []*pb.ClusterInfo
        pods      *pb.PodStats
        alerts    *pb.AlertStats
        pipelines *pb.PipelineStats
    )
    g, ctx := errgroup.WithContext(c.Request.Context())
    g.Go(func() error { var e error; clusters, e  = h.clusterCli.List(ctx);     return e })
    g.Go(func() error { var e error; pods, e      = h.resourceCli.PodStats(ctx); return e })
    g.Go(func() error { var e error; alerts, e    = h.monitorCli.AlertStats(ctx);return e })
    g.Go(func() error { var e error; pipelines, e = h.cicdCli.PipelineStats(ctx);return e })
    if err := g.Wait(); err != nil { c.JSON(500, gin.H{"error": err.Error()}); return }
    c.JSON(200, gin.H{
        "clusters":  clusters,
        "pods":      pods,
        "alerts":    alerts,
        "pipelines": pipelines,
    })
}
```

### 16.7 前端统一请求与错误码

```ts
// @k8s/request/index.ts
import axios from 'axios'
import { ElMessage } from 'element-plus'

export const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '/api/v1',
  timeout: 30000,
  withCredentials: true,
})

request.interceptors.request.use(cfg => {

  cfg.headers.Authorization = `Bearer ${getToken()}`
  if (currentClusterId()) cfg.headers['X-Cluster-ID'] = currentClusterId()
  cfg.headers['X-Trace-ID'] = genTraceId()
  return cfg
})

request.interceptors.response.use(
  res => {
    const { code, data, message } = res.data
    if (code === 0) return data
    if (code === 10101 || code === 10102) { logout(); return }      // Token 失效
    if (code === 20101) { ElMessage.error('权限不足'); throw new BizError(code, message) }
    ElMessage.error(message); throw new BizError(code, message)
  },
  err => {
    // 网关 502/503 → 提示后端服务不可用，由网关熔断兜底
    if (err.response?.status >= 500) ElMessage.error('后端服务暂不可用，请稍后重试')
    return Promise.reject(err)
  }
)
```

## 十七、服务注册发现成熟方案深度对比

面试时只说「用 Consul」是不够的，需要能说出**为什么不用其他**。下面是工业界主流方案的全维度对比。

### 17.1 主流方案对比矩阵

| 维度 | Consul | etcd | Nacos | Zookeeper | Eureka | K8s Service |
|------|--------|------|-------|-----------|--------|-------------|
| 出品方 | HashiCorp | CNCF | 阿里 | Apache | Netflix（停更） | CNCF |
| 一致性协议 | Raft | Raft | Raft / Distro | ZAB | AP（自研） | etcd 底层 |
| CAP | CP/AP 可切 | CP | CP/AP 可切 | CP | AP | CP |
| 健康检查 | HTTP/TCP/gRPC/脚本 | TTL Lease | 客户端心跳 + 服务端探测 | Session | 客户端心跳 | Probe（K8s 原生） |
| 配置中心 | KV ✓ | KV ✓ | ✓（强项） | ✓ | ✗ | ConfigMap/Secret |
| 多数据中心 | ✓ 原生 WAN Gossip | ✗ 需自建 | ✓ | ✗ | ✗ | ✗ |
| Service Mesh | Consul Connect | ✗ | ✗ | ✗ | ✗ | Istio/Linkerd |
| Web 控制台 | ✓ | ✗ | ✓ | ✗ | ✓ | K8s Dashboard |
| Go 客户端成熟度 | 高（官方） | 高（官方） | 中（社区） | 中 | 低 | 高（client-go） |
| 国内运维熟悉度 | 中 | 高（K8s底层） | 高 | 高 | 低 | 高 |

### 17.2 不同场景的推荐选型

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| **纯 K8s 部署，单集群** | K8s Service + DNS | 零成本，无需额外组件 |
| **多 K8s 集群 + 跨机房** | Consul（WAN Federation） | 跨数据中心 Gossip，多 DC 原生支持 |
| **混合 Java/Go 技术栈** | Nacos | 阿里生态，Java 兼容最好，国内文档丰富 |
| **已经使用 K8s + 想做 Mesh** | Istio + K8s Service | Mesh 由 Sidecar 接管发现 |
| **公司已有 etcd 集群** | etcd | 复用已有基础设施 |
| **K8sOperation 当前场景** | **Consul + K8s DNS 双模** | 平台需对接多 K8s 集群，部分跨 VPC |

### 17.3 K8sOperation 平台最终决策

```
┌──────────────────────────────────────────────────────────────┐
│                  K8sOperation 部署形态                         │
│                                                                │
│  ┌────────────────┐         ┌────────────────────────────┐   │
│  │ 平台自身 K8s集群 │         │   被纳管的业务 K8s 集群     │   │
│  │  (k8s-platform) │         │  (cluster-A / B / C ...)   │   │
│  │                │         │                            │   │
│  │  服务发现:      │         │  服务发现:                  │   │
│  │  K8s Service    │         │  resource-svc 通过        │   │
│  │  + DNS          │         │  cluster-svc 拿到 K8s     │   │
│  │                │         │  Client 直接调用 ApiServer │   │
│  │  跨 VPC 时       │         │                            │   │
│  │  fallback Consul│         │                            │   │
│  └────────────────┘         └────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

**决策结论**：
- **平台自身微服务**：使用 **K8s Service + DNS**（零运维成本），通过 Headless Service + gRPC 客户端负载均衡解决长连接打散
- **跨集群/混合云场景**：引入 **Consul**，提供跨 VPC、跨 IDC 的服务注册（被纳管集群本身不需要 Consul Agent，由 cluster-svc 维护连接）
- **配置中心**：K8s ConfigMap/Secret + Consul KV（动态配置走 Consul，静态走 ConfigMap）

### 17.4 Headless Service + gRPC 客户端负载均衡

纯 K8s 模式下，gRPC 长连接默认会粘在某一个 Pod 上，需要使用 Headless Service 让客户端拿到所有 Pod IP：

```yaml

kind: Service
metadata:
  name: auth-svc-headless
spec:
  clusterIP: None              # Headless
  selector: { app: auth-svc }
  ports: [{ name: grpc, port: 50051 }]
```

### 18.1 服务启动完整代码（auth-svc 为例）

```go
// services/auth-svc/cmd/main.go
package main

import (
    "context"
    "net"
    "os"
    "os/signal"
    "syscall"

    "google.golang.org/grpc"
    "go.uber.org/zap"

    pb "k8s_operation/api/auth"
    "k8s_operation/pkg/config"
    "k8s_operation/pkg/database"
    "k8s_operation/pkg/discovery"
    "k8s_operation/pkg/logger"
    "k8s_operation/pkg/middleware"
    "k8s_operation/pkg/registry"
    "k8s_operation/pkg/trace"
    "k8s_operation/services/auth-svc/internal/handler"
    "k8s_operation/services/auth-svc/internal/repository"
    "k8s_operation/services/auth-svc/internal/service"
)

func main() {
    // 1. 加载配置（K8s ConfigMap / Consul KV）
    cfg := config.MustLoad("auth-svc")

    // 2. 初始化日志、链路追踪
    log := logger.MustInit(cfg.Log)
    tp, _ := trace.InitTracer("auth-svc", cfg.Jaeger.Endpoint)
    defer tp.Shutdown(context.Background())

    // 3. 初始化 DB / Redis
    db := database.MustConnect(cfg.Database)
    rdb := database.MustConnectRedis(cfg.Redis)

    // 4. 装配业务层
    repo := repository.NewUserRepo(db)
    sess := repository.NewSessionRepo(rdb)
    svc  := service.NewAuthService(repo, sess, cfg.JWT)
    h    := handler.NewAuthHandler(svc)

    // 5. 启动 gRPC Server（带统一中间件）
    lis, err := net.Listen("tcp", cfg.Server.GRPCAddr)
    if err != nil { log.Fatal("listen failed", zap.Error(err)) }

    grpcSrv := grpc.NewServer(
        grpc.UnaryInterceptor(middleware.UnaryServerInterceptor(log)),
        grpc.StreamInterceptor(middleware.StreamServerInterceptor(log)),
    )
    pb.RegisterAuthServiceServer(grpcSrv, h)

    // 6. 注册到 Consul（仅混合云模式需要）
    if discovery.AutoDetect() == discovery.ModeConsul {
        reg, _ := registry.NewServiceRegistry(cfg.Consul.Addr)
        _ = reg.Register(registry.ServiceConfig{
            Name:    "auth-svc",
            ID:      "auth-svc-" + os.Getenv("POD_NAME"),
            Address: os.Getenv("POD_IP"),
            Port:    50051,
            Tags:    []string{"grpc", "v1"},
        })
        defer reg.Deregister()
    }

    // 7. 优雅关闭
    go func() {
        log.Info("auth-svc started", zap.String("addr", cfg.Server.GRPCAddr))
        if err := grpcSrv.Serve(lis); err != nil {
            log.Fatal("grpc serve failed", zap.Error(err))
        }
    }()

    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    log.Info("shutting down auth-svc...")
    grpcSrv.GracefulStop()
}
```

### 18.3 Proto 代码生成与版本管理

```bash
# scripts/proto-gen.sh
#!/bin/bash
set -e
ROOT=$(cd $(dirname $0)/..; pwd)
cd $ROOT

# 安装插件（一次性）
# go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
# go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# 生成所有 proto
find api -name "*.proto" | while read f; do
  echo "Generating $f ..."
  protoc \
    --proto_path=api \
    --go_out=api --go_opt=paths=source_relative \
    --go-grpc_out=api --go-grpc_opt=paths=source_relative \
    $(echo $f | sed 's|^api/||')
done

echo "✅ Proto generated"
```

**Proto 版本管理建议**：
- `api/` 单独成 Git 子模块或独立仓库（`k8s-platform-api-proto`）
- 每次发布打 tag：`v1.0.0`、`v1.1.0`，向下兼容修改不升大版本
- 字段变更原则：**只增不删**（删除字段保留 reserved），保证滚动升级期间新老版本兼容

**面试表达建议**：先讲收益（独立部署/弹性/故障隔离），再讲成本（治理/链路/事务），最后给出「分阶段、按团队规模演进」的策略，体现工程理性而非追求技术潮流。

## 二十、面试速记卡

> 当面试官问「这个平台的微服务架构怎么设计」时，按这个顺序讲：

1. **先抛业务边界**：平台包含 Auth/RBAC/集群/资源/CICD/监控/AI/商城/镜像 9+ 个领域，单体已无法支撑
2. **再讲拆分原则**：DDD 限界上下文 + 数据库独立 Schema + 服务间禁止跨库 JOIN
3. **服务注册发现选型**：纯 K8s 用 Service+DNS，跨集群混合云用 Consul，**双模封装**屏蔽差异
4. **通信方式**：强一致路径（鉴权、获取连接）走 gRPC；弱一致联动（CICD→静默→通知）走 NATS 事件
5. **网关定位**：Kong 或自研，**JWT 验证 + 限流 + 路由**集中处理，业务服务无感知
6. **前端配套**：Vue3 + 微前端（wujie），各业务团队独立迭代独立发版，BFF 层做接口聚合
7. **演进策略**：Strangler Fig 模式渐进迁移，**Gateway 先并存代理新老两边**，按 Phase 拆分
8. **治理三件套**：OpenTelemetry 链路 + Prometheus 指标 + Loki 日志，统一错误码 + 熔断重试
9. **结尾兜一句**：「微服务不是银弹，团队规模和复杂度匹配才上，否则模块化单体也是好选择」

### 21.4 注册中心选型与安装对比

#### 21.4.1 一句话选型决策

#### 21.4.2 三大主流注册中心实操对比

| 维度 | Consul | etcd | Nacos |
|------|--------|------|-------|
| **安装复杂度** | ★★（单二进制） | ★★（单二进制） | ★★★（依赖 JDK） |

### 21.13 常见环境坑位提醒

| 问题 | 现象 | 解决方案 |
|------|------|----------|
| Consul Agent 无法注册到 Server | `connection refused` | 检查 `bind_addr` 是否为容器 IP，使用 `network_mode: host` 或 `--advertise` 显式指定 |
| Go 模块下载慢 | `i/o timeout` | `export GOPROXY=https://goproxy.cn,direct` |

| NATS JetStream 数据丢失 | 重启后 stream 不见 | 必须挂卷 `--store_dir`，否则消息存内存 |
| MySQL 中文乱码 | 字段值 `???` | 强制 utf8mb4 + utf8mb4_unicode_ci |
| WSL2 Docker Desktop 卡顿 | CPU 100% | `wsl --shutdown` 重启或限制 `.wslconfig` 内存 |
| K8s gRPC 长连接负载不均 | 流量都打到一个 Pod | 使用 Headless Service + `dns:///` + `round_robin` |
| Jenkins Pod 调度失败 | `0/3 nodes are available` | 节点打 label 或修改 nodeSelector，预留 ≥4G 内存 |
| Harbor 镜像推送 401 | `unauthorized: authentication required` | `docker login` 凭据写入 `~/.docker/config.json` |
| Windows PowerShell 启动脚本 `&&` 报错 | 解析错误 | PowerShell 用 `;` 分隔命令 |

## 二十二、Consul 配置与安装实操指南

### 22.1 Consul 地址配置机制

项目中所有微服务（auth-svc / cmdb-svc / gateway-svc）使用**统一的环境变量模式**读取 Consul 地址：

```go
type Config struct {
    HTTPPort   string
    ConsulAddr string
    Env        string
}

func loadConfig() Config {
    return Config{
        HTTPPort:   getEnv("HTTP_PORT", "8081"),
        ConsulAddr: getEnv("CONSUL_ADDR", "localhost:8500"),  // ← 核心配置
        Env:        getEnv("APP_ENV", "development"),
    }
}
```

**配置要点**：
- 环境变量名：`CONSUL_ADDR`
- 格式：`host:port`（不带 `http://` 前缀，代码中拼接 API 时手动添加）
- 默认值：`localhost:8500`

#### 各环境 Consul 地址配置

| 环境 | CONSUL_ADDR 值 | 配置来源 |
|------|----------------|---------|
| 本地开发 | `localhost:8500` | 代码默认值（无需设置） |
| Docker Compose | `consul:8500` | 容器网络内服务名 |
| K8s 集群 | `consul.ops-platform.svc:8500` | Deployment env 注入 |
| 多机房 | `consul-dc1.internal:8500` | 指定数据中心 |

### 22.5 服务注册流程详解

每个微服务启动时通过 Consul HTTP API 注册自身：

```
服务启动 → loadConfig() 读取 CONSUL_ADDR
         → registerToConsul(cfg) 注册服务实例
         → Consul Agent 开始定期健康检查（10s 间隔）
         → 30s 不健康自动注销
         → 服务关闭时调用 deregister() 主动注销
```

注册 Payload 示例：
```json
{
  "ID": "auth-svc-hostname",
  "Name": "auth-svc",
  "Address": "127.0.0.1",
  "Port": 8081,
  "Tags": ["http", "production"],
  "Meta": {"version": "v1.0.0", "protocol": "http"},
  "Check": {
    "HTTP": "http://127.0.0.1:8081/health",
    "Interval": "10s",
    "Timeout": "3s",
    "DeregisterCriticalServiceAfter": "30s"
  }
}
```

### 22.6 服务发现流程详解

其他服务需要调用目标服务时，查询优先级：

```
1. 本地缓存（30s TTL）
   ↓ miss
2. 环境变量直连（如 AUTH_SVC_ADDR=http://127.0.0.1:8081）
   ↓ 未设置
3. Consul HTTP API 查询健康实例
   GET http://{CONSUL_ADDR}/v1/health/service/{name}?passing=true
   ↓ Consul 不可用
4. 硬编码回退地址（仅开发环境兜底）
```

### 22.7 Consul 在微服务中的角色定位

| 能力 | 使用状态 | 说明 |
|------|---------|------|
| **服务注册** | ✅ 已实现 | 所有服务启动时注册 |
| **服务发现** | ✅ 已实现 | gateway-svc / cmdb-svc 动态发现 |
| **健康检查** | ✅ 已实现 | HTTP `/health` 端点探测 |
| **KV 配置中心** | 可选（进阶） | 适合功能开关、限流阈值等动态配置 |
| **Service Mesh** | 未使用 | 需引入 Consul Connect sidecar |

## 二十三、API 网关技术选型与生产建议

### 23.1 当前实现：自研轻量网关

项目当前 `gateway-svc` 基于 Go 标准库 `net/http/httputil.ReverseProxy` 自研，核心能力：

| 能力 | 实现方式 |
|------|---------|
| 路由分发 | 最长前缀匹配 + 路由规则表 |
| 服务发现 | Consul HTTP API + 缓存 + 回退 |
| 认证校验 | 调用 auth-svc VerifyToken |
| 反向代理 | `httputil.ReverseProxy` |
| 跨域处理 | CORS 中间件 |
| 容错 | Panic Recovery + 优雅关闭 |
| 限流 | ❌ 未实现 |
| 熔断 | ❌ 未实现 |
| 灰度路由 | ❌ 未实现 |
| 可观测性 | 日志（无 metrics/tracing） |

**适用阶段**：开发期 / 小规模（<50 QPS），快速验证微服务通信链路。

### 23.2 生产网关选型对比

| 方案 | 语言 | 性能 | 插件生态 | gRPC | 服务发现 | 管理 UI | 推荐场景 |
|------|------|------|---------|------|---------|---------|---------|
| **Kong** | Lua/OpenResty | 高（10w+ QPS） | 200+ 官方/社区插件 | 原生 | Consul/K8s/DNS | Kong Manager | 企业级通用 |
| **APISIX** | Lua/OpenResty | 极高（15w+ QPS） | 80+ 插件 | 原生 | etcd/Consul/Nacos | Dashboard | 国内大厂 |
| **Envoy + Istio** | C++ | 极高 | Filter Chain | 原生 | K8s 原生 | Kiali | Service Mesh |
| **Traefik** | Go | 高 | 中间件 | 原生 | K8s/Consul/Docker | Web UI | K8s 原生 |
| **自研 gateway-svc** | Go | 可控 | 无 | 需实现 | Consul | 无 | 原型验证 |

### 23.3 生产推荐方案

#### 推荐一：Kong Gateway（企业级首选）

```
适用场景：需要完整 API 管理、多团队协作、合规审计

  - 插件开箱即用：限流、熔断、认证、日志、Prometheus metrics
```

```
  - 全动态配置（热加载路由、插件，无需重启）
```

### 23.4 演进路线建议

```
Phase 1（当前）：自研 gateway-svc
```

## 二十四、注册中心替换为 Nacos 指南

### 24.1 Consul vs Nacos 决策矩阵

| 维度 | Consul | Nacos |
|------|--------|-------|
| Go 生态 | 原生支持，SDK 成熟 | SDK 可用（nacos-sdk-go） |
| 健康检查 | Agent 主动探测（HTTP/gRPC/TCP） | 客户端心跳上报 |
| 配置中心 | KV 存储，简单 | 原生配置中心，带版本/灰度/监听 |
| K8s 适配 | Helm 一键部署，Consul Connect | 需额外部署 |
| 多语言 | Go/Java/Python 均有 SDK | Java 最佳，Go 可用 |
| 运维成本 | 单二进制，轻量（<100MB 内存） | Java 进程（至少 1~2GB 内存） |
| UI | 自带 Web UI | 自带 Dashboard（功能更丰富） |
| 适合场景 | Go 微服务 / K8s / 混合云 | Java 生态 / Spring Cloud |

### 24.2 何时选择 Nacos

- 团队有 Java 服务需要接入（Spring Cloud Alibaba 原生集成）
- 需要强配置中心能力（配置版本、灰度推送、监听变更）
- 已有 Nacos 实例可复用
- 不需要 Service Mesh 能力

### 24.3 替换实施步骤

如果决定从 Consul 切换到 Nacos：

1. **安装依赖**：`go get github.com/nacos-group/nacos-sdk-go/v2`
2. **新增 Nacos 注册器**：`pkg/registry/nacos.go`
3. **新增 Nacos 发现客户端**：`pkg/discovery/nacos_resolver.go`
4. **环境变量更改**：`CONSUL_ADDR` → `NACOS_ADDR` + `NACOS_NAMESPACE`
5. **Docker Compose 替换**：

```yaml
# 替换 consul 容器为 nacos
nacos:
  image: nacos/nacos-server:v2.3.0
  container_name: ops-nacos
  ports: ["8848:8848", "9848:9848"]
  environment:
    MODE: standalone
    NACOS_AUTH_ENABLE: "false"
  networks: [ops-net]
```

6. **各服务 main.go 切换**：`registerToConsul` → `registerToNacos`
7. **推荐保持接口抽象**：定义 `Registrar` / `Resolver` 接口，Consul 和 Nacos 各自实现

### 24.4 当前项目建议

本项目以 Go 为主、已部署在 K8s 环境，**建议保留 Consul**：
- Go 生态最契合
- 轻量无额外资源开销
- K8s 内可结合 DNS 模式做零依赖发现
- 项目已有双模发现（K8s DNS + Consul）的完整实现
