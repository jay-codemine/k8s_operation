## 一、限流策略清单

### 1.1 限流中间件位置

| 中间件 | 注册位置 | 作用范围 |
|--------|---------|---------|
| `RateLimit()` | `initialize/server.go` 全局中间件链 | **所有 API 接口**（/api/v1/... 全部） |
| `LoginRateLimit()` | `initialize/router.go` public 路由组 | **仅登录/公开接口**（/auth/login 等） |

### 1.2 通用 API 限流（`RateLimit`）

| 参数 | 值 | 说明 |
|------|----|------|
| 算法 | 令牌桶（Token Bucket） | `golang.org/x/time/rate` 标准库 |
| 速率 | **100 req/s / IP** | 每秒生成 100 个令牌 |
| Burst | **200** | 桶容量，允许短时爆发最多 200 次 |
| 超限响应 | HTTP 429 | `{"code":42900,"msg":"请求过于频繁，请稍后再试"}` |
| 适用场景 | 防止单 IP 恶意刷接口、爬虫等 | |

**触发条件：** 同一 IP 在极短时间内发送超过 200 次请求后，后续请求将被拒绝，直到令牌桶补充。

### 1.3 登录接口限流（`LoginRateLimit`）

| 参数 | 值 | 说明 |
|------|----|------|
| 算法 | 令牌桶（Token Bucket） | `golang.org/x/time/rate` 标准库 |
| 速率 | **1次 / 6秒 / IP** | 即每分钟最多 10 次登录尝试 |
| Burst | **5** | 允许连续最多 5 次，第 6 次起触发限流 |
| 超限响应 | HTTP 429 | `{"code":42901,"msg":"登录尝试过于频繁，请 1 分钟后再试"}` |
| 适用场景 | 防止暴力破解账号密码 | |

**触发条件：** 同一 IP 连续发送超过 5 次登录请求后立即触发，需等待约 6 秒才能再次尝试。

### 1.5 不受限流保护的端点

| 端点 | 说明 |
|------|------|
| `/metrics` | Prometheus 指标抓取（内部 scrape） |
| `/healthz/live` | K8s 存活探针 |
| `/healthz/ready` | K8s 就绪探针 |
| `/swagger/*` | Swagger API 文档 |
| `POST /api/v1/k8s/cicd/pipeline/callback` | Jenkins 构建回调（HMAC 签名验证） |

> 说明：以上端点需要保持无限流以确保 K8s 探针、Prometheus 采集和 Jenkins 回调的正常运行。

### 1.6 内存管理

- 每个 IP 对应一个独立的令牌桶（`sync.Mutex` + `map` 管理）
- **清理策略**：后台 goroutine 每 **5 分钟**扫描一次，删除 **10 分钟**未访问的 IP 条目
- 防止内存无限增长（典型场景：短时间大量不同 IP 扫描后自动清理）

## 二、Jenkins 状态接口 Redis 缓存

### 2.1 问题背景

压测发现 Jenkins 相关接口延迟显著高于纯 DB 查询接口：

| 接口 | QPS | P99 延迟 | 根因 |
|------|-----|---------|------|
| PipelineStatus | 44 | 824ms | 每次实时调用 Jenkins API |
| PipelineStages | 167 | 1133ms | 每次实时调用 Jenkins Workflow API |

### 2.2 缓存策略

**实现文件：** `pkg/cache/jenkins_cache.go`

| 缓存项 | Key 格式 | 运行中 TTL | 已完成 TTL |
|--------|---------|-----------|-----------|
| BuildInfo | `cache:jenkins:build:{pipelineID}:{buildNumber}` | **5s** | **60s** |
| Stages | `cache:jenkins:stages:{pipelineID}:{buildNumber}` | **3s** | **60s** |

**设计原则：**
- 运行中使用短 TTL（3~5s），保证状态刷新及时
- 已完成使用长 TTL（60s），节省 Jenkins API 调用
- Jenkins 回调到达时**主动调用 `InvalidatePipeline()`**清除缓存，确保状态即时更新
- Redis 不可用时**自动降级**到直接调用 Jenkins API，不影响主流程

### 2.3 预期优化效果

| 接口 | 优化前 P99 | 优化后 P99（缓存命中） |
|------|-----------|-------------------|
| PipelineStatus | 824ms | **< 5ms** |
| PipelineStages | 1133ms | **< 5ms** |

## 三、压测报告

### 3.1 测试环境

| 项目 | 说明 |
|------|------|
| 测试工具 | PowerShell 并发脚本（`scripts/benchmark_cicd.ps1`） |
| 并发用户数 | 15 |
| 每用户请求数 | 200 |
| 总请求数 | 3000 次/接口 |
| 测试时间 | 2026-06-20 |

### 3.2 CI/CD 接口压测结果

| API | 并发 | 总请求 | 成功 | 失败 | QPS | 平均延迟 | P50 | P95 | P99 | 最大延迟 |
|-----|------|--------|------|------|-----|---------|-----|-----|-----|---------|
| PipelineList | 15 | 3000 | 3000 | 0 | **766** | 5.3ms | 4ms | 5ms | 13ms | 318ms |
| PipelineHistory | 15 | 3000 | 3000 | 0 | **418** | 6.7ms | 5ms | 8ms | 25ms | 366ms |
| PipelineStatus | 15 | 3000 | 3000 | 0 | **44** | 149.8ms | 35ms | 348ms | 824ms | 26155ms |
| PipelineStages | 15 | 3000 | 3000 | 0 | **167** | 79.6ms | 51ms | 221ms | 1133ms | 1436ms |

### 3.3 结果分析

**DB 查询类接口（优秀）：**
- `PipelineList`：766 QPS，P99 13ms ✅ 远超预期
- `PipelineHistory`：418 QPS，P99 25ms ✅ 性能良好

**Jenkins 实时调用接口（需要缓存优化）：**
- `PipelineStatus`：44 QPS，P99 824ms ⚠️ 瓶颈在 Jenkins API 调用
- `PipelineStages`：167 QPS，P99 1133ms ⚠️ 瓶颈在 Jenkins Workflow API

### 3.4 限流单元测试结果

| 测试用例 | 结果 | 说明 |
|---------|------|------|
| 正常速率无触发 | ✅ PASS | 50次请求全部成功（< burst=200） |
| 爆发超 burst 触发 429 | ✅ PASS | 300次请求：200成功/100被限（精确匹配 burst=200） |
| 多 IP 互不影响 | ✅ PASS | 3个IP各发50次，全部200成功 |
| 登录第6次起触发 | ✅ PASS | 10次请求：5成功/5被限（精确匹配 burst=5） |
| 等待令牌恢复 | ✅ PASS | 限流后等待7秒，请求恢复成功 |

**测试执行时间：7.831s（含7s等待恢复验证）**

### 3.5 容量评估

| 使用场景 | 可支撑能力 | 备注 |
|---------|-----------|------|
| 纯 DB 查询（列表/历史） | **~500-800 QPS** | 资源充足情况下 |
| Jenkins 实时状态查询 | **~40-50 QPS**（未缓存） | Redis 缓存后可达 ~500 QPS |
| 日常使用（50人团队） | ✅ 完全够用 | 峰值估计 < 20 QPS |
| 中型团队（200人） | ⚠️ 建议开启缓存 | 开启后可轻松支撑 |

## 四、运行压测

### 4.1 在 Windows（PowerShell）上运行

```powershell
# 默认参数（10并发 × 50请求）
.\scripts\benchmark_cicd.ps1

# 自定义参数
.\scripts\benchmark_cicd.ps1 -ConcurrentUsers 15 -RequestsPerUser 200 -BaseURL "http://localhost:8080"
```

### 4.2 使用 wrk / hey（Linux/Mac）

```bash
# 安装 hey
go install github.com/rakyll/hey@latest

# 先登录获取 Token
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"123456"}' | jq -r '.data.token')

# 压测流水线列表接口（50并发，1000次）
hey -n 1000 -c 50 \
  -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8080/api/v1/k8s/cicd/pipeline/list?page=1&page_size=10"
```

### 4.3 验证限流触发

```bash
# 快速发送 300 次请求（超过 burst=200 会触发 429）
for i in $(seq 1 300); do
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/api/v1/auth/login \
    -X POST -H "Content-Type: application/json" \
    -d '{"username":"test","password":"test"}'
done | sort | uniq -c
# 期望看到：200个 "200"（或其他成功码），100个 "429"
```
