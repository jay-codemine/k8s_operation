## 1. 功能概述

镜像晋级用于把**一次构建产出的同一个不可变镜像**，按 `dev → test → staging → prod` 的顺序逐级发布到不同环境，而**不重新构建**。

这样做的价值：

- **一致性**：各环境跑的是同一个镜像（同一 digest），杜绝"测试环境是好的，生产又构建出一个不一样的包"。
- **可追溯**：每次晋级都会生成一条发布单（Release），记录来源环境、镜像、操作人、时间。
- **可管控**：预发/生产等敏感环境可开启审批门禁，审批通过后才真正下发部署。

晋级本身**不触发 Jenkins 构建**，而是复用平台的发布单能力（按环境审批 + 多集群下发 + 回滚）。

---

## 2. 核心概念

| 概念 | 说明 |
| --- | --- |
| **环境目标（Target）** | 一条流水线为每个环境（dev/test/staging/prod）预先绑定的部署目标：集群 + 命名空间 + 工作负载 + 容器。存储于 `cicd_pipeline_target` 表。 |
| **不可变镜像** | 构建产出后 tag/digest 固定不变的镜像。晋级时把它原样发布到下一环境。 |
| **晋级链（Chain）** | 各环境目标 + 当前部署镜像/状态的可视化视图，体现镜像逐级流转。 |
| **镜像来源** | 晋级时镜像从哪里来，三选一：最新构建产物 / 上游环境当前镜像 / 手动指定。 |
| **审批门禁** | 环境的 `require_approval=true` 时，晋级到该环境会先进入审批流程。 |
| **发布单（Release）** | 晋级的落地载体，复用发布管理的审批、下发、回滚能力。 |

## 3. 前置条件

在开始晋级前，请确认：

1. **已有可用集群**：平台「集群管理」中已接入至少一个 K8s 集群（各环境可用不同集群）。
2. **目标工作负载已存在**：每个环境要部署到的 `Deployment/StatefulSet/DaemonSet` 已经在对应集群/命名空间中存在（晋级是"更新已存在工作负载的镜像"，不是从零创建）。
3. **流水线已成功构建过至少一次**：镜像来源选「最新构建产物」时，需要有一条 `build_number > 0` 且包含镜像产物的运行记录。
4. **数据库表已就绪**：`cicd_pipeline_target` 表存在（完整初始化 SQL `docs/sql/k8s_platform_full_init.sql` 已包含该表）。

## 4. 操作流程总览

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 1. 配置环境目标 │ ──▶ │ 2. 晋级镜像      │ ──▶ │ 3.（如需）审批  │ ──▶ 部署下发
│  绑定各环境集群 │     │  选择来源+目标   │     │  预发/生产门禁  │
│  /命名空间/负载 │     │  提交晋级        │     │  通过后执行     │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

第一次使用只需做一次「步骤一」，之后每次发版只做「步骤二」。

## 5. 步骤一：配置环境部署目标

### 5.1 入口

流水线详情页 → **镜像晋级** 标签页 → 右上角 **「配置环境目标」** 按钮。

### 5.2 首次进入的默认模板

若该流水线还没配置过环境目标，弹窗会自动预填一份**默认模板**（4 个环境），并从流水线自身的部署目标带出集群/命名空间/工作负载：

| 环境 | 默认自动部署 | 默认审批 | 默认上游来源 |
| --- | --- | --- | --- |
| dev（开发） | ✅ 自动 | ❌ | 无（首环境） |
| test（测试） | ❌ | ❌ | dev |
| staging（预发） | ❌ | ✅ 需审批 | test |
| prod（生产） | ❌ | ✅ 需审批 | staging |

> 默认模板只是便捷起点。**请务必把每个环境改成各自真实的目标**（不同集群 / 不同命名空间 / 不同工作负载）。

### 5.3 每列含义

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 环境 | ✅ | dev / test / staging / prod，同一流水线内不可重复 |
| 集群 | ✅ | 该环境部署到的目标集群 |
| 命名空间 | ✅ | 目标命名空间（留空默认 `default`） |
| 类型 | ✅ | 工作负载类型：Deployment / StatefulSet / DaemonSet |
| 工作负载 | ✅ | 要更新镜像的工作负载名称（须在目标集群已存在） |
| 容器 | ❌ | 要替换镜像的容器名（留空默认与工作负载同名） |
| 来源 | ❌ | 上游环境，用于"从上游晋级"；首环境留空 |
| 审批 | ❌ | 勾选后晋级到该环境需审批 |

### 5.4 保存

点击 **「保存配置」**。保存采用**全量覆盖**语义：

- 提交列表中存在的环境 → 新增或更新；
- 之前存在、这次没提交的环境 → 自动软删除。

保存成功后，晋级链会立即刷新出对应的环境卡片。

---

## 6. 步骤二：晋级镜像

### 6.1 入口

在晋级链上，点击目标环境卡片下方的 **「晋级到 XX」** 按钮，打开晋级弹窗。

弹窗顶部的**流转横幅**会清晰标明：`来源 → 目标环境`。

### 6.2 镜像来源（三选一）

| 来源 | 适用场景 | 说明 |
| --- | --- | --- |
| **最新构建产物** | 首次把新构建发到 dev/test | 填运行记录 ID；**留空 = 自动使用该流水线最近一次已构建的镜像** |
| **从上游晋级** | test→staging→prod 逐级晋级 | 取上游环境当前正在运行的镜像（保证同一不可变镜像流转）。仅当上游已有部署时出现该选项 |
| **手动指定** | 特殊情况指定任意镜像 | 手填镜像仓库 + Tag（可选 Digest） |

> 提示：从上游晋级是最推荐的方式，它天然保证"生产跑的就是预发验证过的同一镜像"。

### 6.3 填写晋级说明

建议填写本次晋级原因，例如"验收通过，晋级至生产"，便于后续审计追溯。

### 6.4 提交

点击 **「确认晋级」**：

- **目标环境未开启审批** → 直接生成发布单并入队部署；
- **目标环境开启审批** → 生成发布单并进入**审批流程**，审批通过后才执行部署（弹窗会有黄色提示）。

提交成功后晋级链自动刷新，可看到该环境的最新发布状态。

---

## 7. 审批流程

当目标环境 `require_approval=true`：

1. 晋级提交后，发布单状态为 **待审批（AwaitingApproval）**。
2. 审批人在「发布管理 / 审批」中处理（若配置了飞书审批，会推送审批卡片）。
3. **审批通过** → 发布单进入排队/部署，镜像下发到目标集群工作负载。
4. **审批拒绝** → 发布单终止，不下发。

> 建议：预发（staging）、生产（prod）默认开启审批；开发（dev）、测试（test）可关闭以提升效率。

---

## 8. 晋级链可视化解读

晋级链把每个环境渲染成一张卡片，横向按 `dev → test → staging → prod` 排列。

**环境卡片**

- **顶部色条**：dev 绿 / test 蓝 / staging 橙 / prod 红。
- **标签**：`⚡ 自动`（CI 成功后自动部署）、`🔒 需审批`（晋级需审批）。
- **当前版本 chip**：正在运行的镜像 tag/digest + 状态灯：
  - 🟢 已部署（Succeeded） 🔵 部署中（Running/Queued） 🔴 失败（Failed） 🟡 待审批/待处理
- **集群 / 负载**：该环境的部署目标（命名空间/工作负载）。
- **尚未部署**：该环境还没有任何发布单。

**连接线**

- 普通箭头 `→`：同一镜像逐级晋级。
- 🔒 门禁锁：下一环境需审批。

发布状态含义：

| 状态 | 含义 |
| --- | --- |
| Pending | 待处理 |
| AwaitingApproval | 待审批 |
| Queued | 排队中 |
| Running | 部署中 |
| Succeeded | 已部署 |
| Failed | 失败 |
| Canceled | 已取消 |
| Rollback | 已回滚 |

## 9. 典型场景演练

### 场景：新版本从开发一路发到生产

假设流水线 `k8soperation-web` 已配好 4 个环境目标。

1. **构建**：在流水线执行一次构建，产出镜像 `registry/k8soperation-web:v1.2.0`。
2. **发到 dev**：晋级到「开发」→ 来源选「最新构建产物」→ 留空 → 确认。dev 卡片显示 `v1.2.0 / 已部署`。
3. **发到 test**：晋级到「测试」→ 来源选「从上游(dev)晋级」→ 确认。test 显示同一 `v1.2.0`。
4. **发到 staging**：晋级到「预发」→ 从上游(test)晋级 → 确认。因 staging 需审批 → 进入审批 → 通过后部署。
5. **发到 prod**：晋级到「生产」→ 从上游(staging)晋级 → 确认 → 审批通过 → 部署。

全过程只构建了 1 次，4 个环境跑的都是 `v1.2.0` 同一镜像。

## 10. 接口参考（API）

所有接口前缀：`/api/v1/k8s/cicd/promote`，需登录鉴权。

### 10.1 获取环境目标列表

```
GET /api/v1/k8s/cicd/promote/targets?pipeline_id={id}
```

响应：`{ "code":0, "data": { "list": [ ...target ] } }`

### 10.2 保存环境目标（全量覆盖）

```
POST /api/v1/k8s/cicd/promote/targets/save
```

请求体（`PipelineTargetSaveRequest`）：

```json
{
  "pipeline_id": 6,
  "targets": [
    {
      "env": "dev",
      "cluster_id": 1,
      "namespace": "dev",
      "workload_kind": "Deployment",
      "workload_name": "k8soperation-web",
      "container": "k8soperation-web",
      "auto_deploy": true,
      "require_approval": false,
      "promote_from": "",
      "sort_order": 1
    },
    {
      "env": "prod",
      "cluster_id": 2,
      "namespace": "prod",
      "workload_kind": "Deployment",
      "workload_name": "k8soperation-web",
      "container": "k8soperation-web",
      "auto_deploy": false,
      "require_approval": true,
      "promote_from": "staging",
      "sort_order": 4
    }
  ]
}
```

### 10.3 删除单个环境目标

```
POST /api/v1/k8s/cicd/promote/targets/delete
Body: { "id": 12 }
```

### 10.4 镜像晋级

```
POST /api/v1/k8s/cicd/promote/run
```

请求体（`PipelinePromoteRequest`），镜像来源优先级：**显式镜像 > source_release_id > source_run_id > 最新已构建**：

```json
{
  "pipeline_id": 6,
  "target_env": "staging",
  "source_run_id": 0,
  "source_release_id": 0,
  "image_repo": "",
  "image_tag": "",
  "image_digest": "",
  "reason": "验收通过，晋级至预发"
}
```

| 字段 | 说明 |
| --- | --- |
| `pipeline_id` | 流水线 ID（必填） |
| `target_env` | 目标环境 dev/test/staging/prod（必填） |
| `source_run_id` | 从某次构建运行记录晋级；**传 0 或留空 = 自动取最新已构建镜像** |
| `source_release_id` | 从已有发布单晋级（跨环境晋级用） |
| `image_repo`/`image_tag`/`image_digest` | 手动指定镜像 |
| `reason` | 晋级说明 |

响应：`{ "code":0, "data": { "release_id": 33, "message": "镜像晋级已提交（如目标环境需审批则进入审批流程）" } }`

### 10.5 获取晋级链

```
GET /api/v1/k8s/cicd/promote/chain?pipeline_id={id}
```

响应 `data.chain` 为各环境节点数组，含 `env / cluster_name / namespace / workload_name / require_approval / auto_deploy / current_release_id / current_image_repo / current_image_tag / current_release_status / current_deploy_time` 等字段。

## 11. 数据表说明

### `cicd_pipeline_target` —— 流水线环境部署目标

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint unsigned | 主键 |
| pipeline_id | bigint | 所属流水线 |
| env | varchar | 环境标识 dev/test/staging/prod |
| cluster_id | bigint | 目标集群 |
| namespace | varchar | 命名空间 |
| workload_kind | varchar | 工作负载类型 |
| workload_name | varchar | 工作负载名称 |
| container | varchar | 容器名 |
| auto_deploy | tinyint | 是否自动部署 |
| require_approval | tinyint | 是否需审批 |
| promote_from | varchar | 上游来源环境 |
| sort_order | int | 排序 |
| created_user_id | bigint | 创建人 |
| created_at / modified_at / deleted_at | bigint unsigned | 时间戳 |
| is_del | tinyint unsigned | 软删除标志 |

> 唯一约束逻辑：同一 `pipeline_id + env` 只保留一条有效记录（保存时按此 upsert）。

晋级产生的发布记录写入 `cicd_release` 表（含 `env`、`source_env`、`source_run_id` 等晋级链追踪字段）。

## 12. 常见问题与故障排查

### Q1：点「确认晋级」报 `请指定镜像来源：source_run_id / source_release_id / image_repo 三选一`

- **原因（旧版本）**：来源选「最新构建产物」且运行记录 ID 留空，但流水线还没成功构建过。
- **现版本行为**：留空会**自动取最近一次已构建镜像**；若确实一次都没构建过，会提示"流水线暂无可晋级的构建产物，请先成功执行一次构建后再晋级"。
- **处理**：先在流水线执行一次成功构建，再晋级。

### Q2：报 `环境[xxx]未配置部署目标`

该环境还没在「配置环境目标」中绑定集群/命名空间/工作负载。先完成步骤一。

### Q3：报 `Table 'xxx.cicd_pipeline_target' doesn't exist`

数据库缺表。执行完整初始化 SQL `docs/sql/k8s_platform_full_init.sql`，或单独建 `cicd_pipeline_target` 表。注意确认后端实际连接的数据库（部署环境通常读 `deploy/backend/secret.yaml` 中的库，而非本地 `config.yaml`）。

### Q4：晋级链页面接口 400 / `pipeline_id=NaN`

流水线 ID 未正确传入。刷新详情页重进；若自建集成，确认 `pipeline_id` 为有效数字。

### Q5：晋级后一直「待审批」

目标环境开启了审批。到「发布管理 / 审批」处理；若接了飞书审批，在审批卡片中通过。

### Q6：晋级成功但工作负载镜像没变

- 确认目标 `workload_name` / `namespace` / `container` 与集群中实际工作负载一致；
- 查看该发布单状态是否 Failed，并看错误信息（容器名不匹配、镜像拉取失败、集群不可达等）。

### Q7：各环境显示的工作负载都一样

首次配置时默认模板从流水线自身目标克隆到了所有环境。请在「配置环境目标」中把各环境改成真实的集群/命名空间/工作负载。
