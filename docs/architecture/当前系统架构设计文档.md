## 二、平台总体定位

### 2.1 核心价值

解决多集群管理分散、权限隔离困难、运维效率低下三大痛点，集成 AI 智能助手实现自然语言运维。

### 2.2 核心能力矩阵

| 能力域 | 能力点 |
|--------|--------|
| 多集群治理 | 多集群资源管理、三层 RBAC（平台→集群→命名空间）、KubeConfig 加密存储 |
| CI/CD 闭环 | 14 阶段全链路流水线、SonarQube 质量门禁、Harbor 镜像、Jenkins 集成、人工审批 |
| 监控告警 | Prometheus 双链路告警、多群路由、批量绑定、静默、CICD 联动 |
| AI 智能化 | OpenAI Function Calling、AIOps 智能巡检、自然语言操作 K8s |
| 容器交互 | xterm.js + WebSocket 容器终端、实时状态监听 |
| 应用治理 | 应用商城（Helm/YAML 多组件）、构建探针管理、CRD/CR 动态资源管理 |
| 平台运营 | 审计日志、健康检查、系统设置、镜像仓库管理 |

## 六、启动与生命周期

### 6.1 入口流程（cmd/k8soperation/main.go）

```go
func main() {
    if err := bootstrap.InitAll(); err != nil { panic(err) }
    defer func() {
        bootstrap.StopCicdWorker()
        bootstrap.FlushLoggers()
    }()
    srv := server.NewHTTPServer()
    server.ListenAndServeAsync(srv)
    timeout := global.ServerSetting.ShutdownTimeout * time.Second
    if timeout <= 0 { timeout = 5 * time.Second }
    server.GracefulShutdown(srv, timeout)
}
```

### 6.2 InitAll 启动编排顺序

```
1.  SetupSetting           读取 configs/config.yaml
2.  SetupValidator         注册自定义校验规则
3.  SetupLogger            初始化 zap 三日志器（System/Biz/AI）
4.  注入 AILogger          openai.AILog = global.AILogger
5.  SetupDB                MySQL 连接池建立 + AutoMigrate
6.  BootstrapMonitorDS     首次启动将 PrometheusURL 引导至 DB
7.  SetupSession           Redis Session 中间件
8.  SetupRedis             Redis 客户端（核心依赖，失败终止）
9.  SetupK8sBootstrap      多集群 Client 初始化（失败仅警告）
10. SetupAppConfigClient   AppConfig CRD 客户端
11. LogDocsReady           Swagger 文档加载
12. StartCicdWorker        CICD 任务消费 + Pipeline 轮询
13. SyncApprovalData       历史审批数据补全
14. AuditCleanupWorker     审计日志定期清理
15. AlertEvalWorker        Prometheus 告警评估循环
16. AIOpsInspectionWorker  6h 周期 AI 智能巡检（可选）
```

### 6.3 优雅关闭

由 `server.GracefulShutdown` 负责：
1. 停止接收新请求
2. 停止 5 个 Worker（CICD / PipelinePoll / AuditCleanup / AlertEval / AIOpsInspection）
3. Flush 三个日志器（系统/业务/AI）
4. 关闭 SQL DB 连接（通过 `srv.RegisterOnShutdown`）

## 八、多集群路由机制

### 8.1 ClusterMiddleware 工作流程

```go
// middlewares/cluster.go
1. 从 X-Cluster-ID Header / clusterId Query 获取 clusterID
2. 校验 clusterID 合法性
3. 取当前用户 user_id
4. 推断当前 action（view/create/update/delete/exec）
5. 调用 svc.CheckClusterPermission 校验权限（不通过返回 403 + Prometheus 埋点）
6. factory.Get(ctx, clusterID) 从连接池获取 K8s Client
7. 错误映射：not found → 404、forbidden → 403、连接失败 → 503
8. 注入 ctx：cluster_id / k8s_clients / cluster_action
9. 进入业务 Handler
```

### 8.2 ClusterClientFactory 连接池

| 特性 | 实现 |
|------|------|
| 缓存粒度 | 按 clusterID 缓存一组 Client（kube/dynamic/metrics） |
| 复用策略 | TTL（默认 30m）+ TTLJitter（默认 3m），防雪崩 |
| KubeConfig 加载 | 从 DB 读取加密 KubeConfig，解密后构造 RestConfig |
| 健康标识 | SupportsEvV1（事件 v1 支持）、has_metrics |
| 失败处理 | 错误降级为日志，不阻塞登录 / RBAC / CICD |

### 13.1 中间件执行顺序


### 13.2 错误码规范

- 通用错误（参数校验/未授权）
- 集群错误（不存在/不可达）
- CICD 错误（构建失败/超时）
- 监控错误（规则无效/查询失败）
- AI 错误（API 限额/工具不存在）

## 十七、当前架构特征评价

### 17.1 优势

| 维度 | 优势 |
|------|------|
| 部署 | 单二进制，依赖少，部署/调试简单 |
| 性能 | 进程内调用零开销，事务边界清晰 |
| 一致性 | 统一 GORM DB，强一致 |
| 链路 | 调用链路短，问题定位方便 |
| 演进 | 内部模块边界清晰（Routers/Services/DAO 分层），具备演进基础 |

### 17.2 局限

| 维度 | 局限 |
|------|------|
| 弹性 | 无法按模块独立扩缩容（AI 与 CICD 资源诉求差异大） |
| 隔离 | 一处 OOM/死循环影响全平台（已有 Recovery 兜底，但仍有风险） |
| 协作 | 多人/多团队迭代时易冲突（services 目录已 58 个文件） |
| 发布 | 任意模块改动需整体重启 |
| 阻塞 | OpenAI 长任务、Prometheus 大查询会占用主进程线程资源 |
| 数据库 | 共享一个 Schema，热点表（cicd_pipeline_run、audit_log）随时间增长 |

### 17.3 演进方向

详见同目录 [微服务架构拆分与服务注册发现设计文档.md](file:///D:/k8s-go/k8s_operation/docs/微服务架构拆分与服务注册发现设计文档.md)，采用 **Strangler Fig 模式**：
1. Phase 1：基础设施（Consul/NATS）+ 拆出 Auth/RBAC/Gateway
2. Phase 2：拆出 Cluster/Resource/Monitor/Notify
3. Phase 3：拆出 CICD/AI/AppStore/Image，下线单体
4. Phase 4：Service Mesh + 全链路灰度 + 混沌工程

### 18.2 重要约定

- **后端健康检查端点**：`/healthz/live`
- **CICD 回调路由**：必须放在 `cicdGroup` 之前注册（Gin 路由树继承中间件机制）
- **Swagger @Param paramType**：必须为 `formData`
- **Jenkins Job Script Path**：必须与语言类型严格匹配
- **K8s 工作负载状态判定**：必须基于 `Conditions` 而非仅 `replicas` 对比
- **多资源 YAML 创建**：自动统一命名空间、按依赖顺序创建
