## 二、作业平台模块设计与接入

### 2.1 作业平台是什么

作业平台（Job Platform）是运维管理平台的**批量运维执行中枢**，负责：

- 批量对多台主机/Pod 执行命令（如批量重启、批量检查）
- 脚本模板管理与版本控制
- 定时/手动触发作业调度
- 执行结果实时流式输出（类似 Ansible Tower）
- 高危操作需人工审批（与工单系统联动）
- 完整的执行历史和审计追踪

### 2.2 作业平台功能模块设计

```
作业平台（job-platform）
│
├── 脚本管理
│   ├── 脚本库：Shell/Python/Ansible 脚本模板
│   ├── 版本控制：脚本历史版本对比
│   └── 变量注入：执行时动态填写参数
│
├── 执行目标管理
│   ├── 主机目标：SSH 连接主机清单
│   ├── Pod 目标：K8s Pod exec 批量执行
│   └── 目标分组：按环境/业务线分组
│
├── 作业调度
│   ├── 手动执行：即时触发
│   ├── 定时执行：Cron 表达式调度
│   └── 事件触发：告警联动自动执行
│
├── 执行引擎
│   ├── 并发控制：滚动执行/全量并发可配置
│   ├── 失败策略：失败停止/失败继续/人工确认
│   ├── 实时输出：WebSocket 推送执行日志
│   └── 执行超时：可配置超时时间
│
└── 审批流程
    ├── 高危操作识别：rm/reboot/shutdown 等关键字
    ├── 工单审批：与工单系统 API 集成
    └── 紧急通道：紧急执行绕过审批（需特权角色）
```

### 2.5 作业平台 K8s Pod 执行实现

```go
// services/job_executor.go
// 复用现有的 ClusterClientFactory，直接调用 Pod exec API

func (e *JobExecutor) ExecOnPod(ctx context.Context, clusterID int64,
    namespace, podName, container string, command []string) (string, error) {

    // 1. 从 ClusterClientFactory 获取集群客户端（复用现有逻辑）
    client, err := e.factory.GetClient(clusterID)
    if err != nil {
        return "", err
    }

    // 2. 构建 exec 请求（和容器终端一样的实现）
    req := client.CoreV1().RESTClient().Post().
        Resource("pods").
        Name(podName).
        Namespace(namespace).
        SubResource("exec").
        VersionedParams(&corev1.PodExecOptions{
            Container: container,
            Command:   command,
            Stdout:    true,
            Stderr:    true,
        }, scheme.ParameterCodec)

    // 3. 执行并收集输出
    exec, _ := remotecommand.NewSPDYExecutor(client.RestConfig, "POST", req.URL())
    var stdout, stderr bytes.Buffer
    exec.StreamWithContext(ctx, remotecommand.StreamOptions{
        Stdout: &stdout,
        Stderr: &stderr,
    })
    return stdout.String() + stderr.String(), nil
}
```

## 三、渐进式微服务架构设计原则

### 3.1 核心思想：设计可演进的「模块化单体」

> **不要从一开始就做微服务，但要从一开始就按微服务的边界写单体。**
>
> 这种架构叫 **Modular Monolith（模块化单体）**，是大厂在系统初期的标准做法。

**三个核心原则：**

```
原则 1：模块间只通过接口通信，不直接调用对方的 struct
原则 2：每个模块有独立的数据表，不做跨模块的 JOIN 查询
原则 3：模块间的调用通过「内部事件总线」而非直接函数调用
```

### 3.2 模块化单体 vs 微服务 对比

```
模块化单体（现在）：
    ┌─────────────────────────────────────────┐
    │  单个进程                                │
    │  ┌──────┐  接口调用  ┌──────┐           │
    │  │模块A │ ─────────▶ │模块B │           │
    │  └──────┘            └──────┘           │
    │  同一个 DB，不同 Schema/前缀             │
    └─────────────────────────────────────────┘

微服务（未来）：
    ┌──────────┐   HTTP/gRPC   ┌──────────┐
    │ 服务 A   │ ─────────────▶ │ 服务 B   │
    │ 进程 A   │               │ 进程 B   │
    │ DB_A     │               │ DB_B     │
    └──────────┘               └──────────┘

关键区别：只需要把「接口调用」改成「HTTP调用」，DB 分开即可
如果一开始就用接口通信，迁移成本极低！
```

### 3.3 防腐层设计（Anti-Corruption Layer）

这是让单体可快速演进为微服务的**最关键设计**：

```go
// 错误做法（直接依赖）：耦合死，无法拆分
type CicdService struct {
    userSvc  *services.UserService    // 直接依赖具体 struct
    alertSvc *services.MonitorService // 直接依赖具体 struct
}

// 正确做法（接口依赖）：可随时替换为 HTTP 调用
type CicdService struct {
    userSvc  UserInfoPort    // 依赖接口
    alertSvc AlertSilencePort // 依赖接口
}

// 接口定义
type UserInfoPort interface {
    GetUserByID(ctx context.Context, id int64) (*UserInfo, error)
    GetUsersByIDs(ctx context.Context, ids []int64) ([]*UserInfo, error)
}

type AlertSilencePort interface {
    CreateSilence(ctx context.Context, req *CreateSilenceRequest) error
    DeleteSilence(ctx context.Context, id string) error
}

// 单体阶段：本地实现（直接调用 DB）
type LocalUserInfoAdapter struct {
    db *gorm.DB
}
func (a *LocalUserInfoAdapter) GetUserByID(ctx context.Context, id int64) (*UserInfo, error) {
    // 直接查 DB
}

// 微服务阶段：HTTP 实现（改这一个文件，业务代码零修改）
type RemoteUserInfoAdapter struct {
    baseURL string
    client  *http.Client
}
func (a *RemoteUserInfoAdapter) GetUserByID(ctx context.Context, id int64) (*UserInfo, error) {
    // HTTP 调用 user-svc
}
```

### 3.4 内部事件总线（为消息队列做准备）

```go
// pkg/eventbus/eventbus.go
// 单体阶段用内存事件总线，微服务阶段换成 Kafka/NATS，业务代码不变

type EventBus interface {
    Publish(ctx context.Context, topic string, event interface{}) error
    Subscribe(topic string, handler EventHandler) error
}

// 单体阶段：内存实现
type InMemoryEventBus struct {
    handlers map[string][]EventHandler
    mu       sync.RWMutex
}

func (b *InMemoryEventBus) Publish(ctx context.Context, topic string, event interface{}) error {
    b.mu.RLock()
    handlers := b.handlers[topic]
    b.mu.RUnlock()
    for _, h := range handlers {
        go h(ctx, event) // 异步执行，模拟 MQ 行为
    }
    return nil
}

// 微服务阶段：Kafka 实现（替换注入的实例即可）
type KafkaEventBus struct {
    producer sarama.SyncProducer
}

// 使用方式（业务代码不变）：
// 发布：eventBus.Publish(ctx, "cicd.pipeline.finished", &PipelineEvent{...})
// 订阅：eventBus.Subscribe("cicd.pipeline.finished", alertSilenceHandler)
```

### 4.2 模块内部分层规范

```go
// internal/app/modules/job/ports.go
// 声明该模块依赖的外部能力（通过接口，不直接依赖其他模块）

package job

import "context"

// K8sPort 依赖 K8s 执行能力
type K8sPort interface {
    ExecOnPod(ctx context.Context, clusterID int64, namespace, pod, container string, cmd []string) (string, error)
    ListPods(ctx context.Context, clusterID int64, namespace string) ([]PodInfo, error)
}

// UserPort 依赖用户信息查询
type UserPort interface {
    GetUserByID(ctx context.Context, userID int64) (*UserInfo, error)
}

// NotifyPort 依赖消息通知能力
type NotifyPort interface {
    SendNotification(ctx context.Context, userID int64, title, content string) error
}

// ApprovalPort 依赖审批能力（工单系统）
type ApprovalPort interface {
    CreateApproval(ctx context.Context, req *ApprovalRequest) (string, error)
    GetApprovalStatus(ctx context.Context, approvalID string) (string, error)
}
```

```go
    notify   NotifyPort     // 消息通知（注入）
    approval ApprovalPort   // 审批流程（注入，可选）
    eventBus EventBus       // 事件总线（注入）
}

func NewJobService(repo JobRepository, k8s K8sPort, user UserPort,
    notify NotifyPort, eventBus EventBus) *JobService {
    return &JobService{
        repo:     repo,
        k8s:      k8s,
        user:     user,
        notify:   notify,
        eventBus: eventBus,
    }
}

// ExecuteTask 执行作业任务
func (s *JobService) ExecuteTask(ctx context.Context, taskID int64) error {
    task, err := s.repo.GetTaskByID(ctx, taskID)
    if err != nil {
        return err
    }

    // 通过接口调用 K8s，后期拆分时改为 HTTP 调用，这里不变
    for _, target := range task.PodTargets {
        output, err := s.k8s.ExecOnPod(ctx, target.ClusterID,
            target.Namespace, target.PodName, target.Container, task.Command)
        s.repo.SaveExecution(ctx, &JobExecution{
            TaskID: taskID, Target: target.PodName,
            Output: output, Status: statusOf(err),
        })
    }

    // 通过事件总线发布完成事件（后期换 Kafka，这里不变）
    s.eventBus.Publish(ctx, "job.task.finished", &JobFinishedEvent{
        TaskID: taskID, Status: task.Status,
    })
    return nil
}
```

## 五、微服务拆分路径与时机判断

### 5.1 拆分时机判断矩阵

| 判断条件 | 分值 | 说明 |
|---------|------|------|
| 该模块有独立的高并发压力 | +3 | 如 CICD 构建高峰期 |
| 该模块需要独立扩缩容 | +3 | 如 AI 助手 GPU 资源 |
| 该模块有独立的发布节奏 | +2 | 多团队并行开发 |
| 该模块对其他模块有强依赖 | -2 | 拆了也是分布式单体 |
| 该模块数据与其他模块强耦合 | -3 | 拆了还是要跨库 JOIN |
| 团队规模 < 5人 | -3 | 微服务运维成本高于收益 |

**评分 ≥ 3 分才值得拆分。**

### 5.2 k8s_operation 各模块拆分优先级

```
优先级排序（从高到低）：

🔴 高优先（分值高，先拆）：
   CI/CD 流水线服务（cicd-svc）
   ├── 构建任务 CPU 密集，独立扩容
   ├── Worker 数量可弹性调整
   └── Jenkins 集成相对独立

   AI 助手服务（ai-svc）
   ├── OpenAI 调用延迟高，独立隔离
   ├── 内存消耗大（模型上下文）
   └── 独立限流（API Key 配额管理）

🟡 中优先（团队扩大后再拆）：
   监控告警服务（monitor-svc）
   ├── 告警 Worker 独立运行
   └── Prometheus/Loki 集成独立

   作业平台服务（job-svc）
   ├── SSH/Pod exec 并发需求
   └── 执行结果存储独立

🟢 低优先（保持合并）：
   K8s 资源管理（稳定，低频变更）
   镜像管理（功能简单）
   应用商城（稳定）
   平台管理（配置类，低频）

❌ 不建议拆：
   用户认证与权限
   ├── 所有其他服务都依赖它
   ├── 拆了会引入网络延迟到每次请求
   └── 建议：做成共享 JWT 库，不拆服务
```

### 5.3 推荐的拆分步骤（以 CICD 为例）

```
Step 1：确认模块边界清晰（已完成 ✅）
    - cicd_pipeline.go 等 13 个服务文件已隔离
    - cicd_*表 与其他模块无 JOIN

Step 2：抽取接口（防腐层）
    - 定义 UserPort、K8sDeployPort、AlertSilencePort 接口
    - 将 cicd_pipeline.go 中的直接调用替换为接口调用
    - 用本地适配器实现接口（功能不变）

Step 3：独立目录编译验证
    - 将 cicd 相关代码移入 services/cicd/ 子目录
    - 确认 go build 通过，测试通过

Step 4：独立进程启动（仍共享 DB）
    - 新建 cmd/cicd-worker/main.go
    - 只启动 CICD Worker + CICD Handler
    - 两个进程共用同一个 MySQL（过渡阶段）

Step 5：数据库分离
    - 将 cicd_* 表迁移到独立 MySQL 实例
    - 其他模块通过 HTTP 接口获取 CICD 状态

Step 6：API Gateway 路由
    - /api/v1/k8s/cicd/* → cicd-svc:8083
    - 其他路由保留在主服务
```

## 八、核心结论

> **三句话总结：**
>
> 1. **现在不要微服务**：你的平台当前代码结构已经很好，9个模块边界清晰，
>    先把「接口防腐层」和「事件总线」加上，单体就已经具备了随时拆分的能力。
>
> 2. **接入新公司只需三件事**：改 `auth.go` 认证对接 + `router.go` 加路由前缀 +
>    注册到 Consul/Nacos，就能立即接入任何统一平台。
>
> 3. **作业平台按模块化单体先接入**：复用现有 ClusterClientFactory 做 Pod exec，
>    复用 Redis Stream 做异步执行，3-5 天可以出可用版本，
>    后期根据并发压力决定是否独立部署。
