# 统一运维平台微服务架构设计文档

> 适用场景：新公司从零设计统一运维平台（OpsPlatform），后端 Go，前端 Vue3。
> 核心理念：**平台底座 + 插拔式能力模块**，按业务域拆分微服务，配套统一门户与 API 网关。

---

## 一、文档说明

| 属性 | 内容 |

### 2.2 设计核心理念

1. **平台底座下沉**：用户、权限、审计、消息、配置 5 大公共能力沉淀为底座，所有业务模块复用，避免重复造轮子。
2. **业务能力插拔**：CMDB、CI/CD、监控、作业、工单等业务模块边界清晰，可按需启停，新增能力（成本分析、容量管理、AI 运维）通过同一套接口规范接入。
3. **模块化单体兜底**：团队规模 < 5 人或业务复杂度低时，以**模块化单体**起步（同一仓库分包，预留拆分点），业务跑顺再渐进式拆为微服务。
4. **数据独立**：每个微服务独占 DB Schema，禁止跨服务直连数据库，必须通过 API/事件交互。
5. **CMDB 是数据底座**：所有业务模块的"资产元数据"都来自 CMDB，CMDB 的稳定性 = 平台稳定性。

## 三、业务域与微服务划分

### 3.1 八大业务模块清单

| 模块 | 服务名 | 核心职责 | 数据库 | 通信方式 | 关键依赖 |
|------|--------|---------|--------|---------|---------|
| **用户中心** | `auth-svc` | 登录、注册、JWT、SSO、组织架构、用户 CRUD | `auth_db` | gRPC | LDAP/OAuth2 |
| **权限中心** | `rbac-svc` | 角色、权限点、资源绑定、鉴权判定 | `rbac_db` | gRPC | Casbin |
| **CMDB 资产中心** | `cmdb-svc` | 资产模型、CI 项、关系拓扑、变更追溯 | `cmdb_db` | gRPC + 事件 | Neo4j（可选） |
| **CI/CD 发布中心** | `cicd-svc` | 流水线、构建、发布、制品、回滚、审批触发 | `cicd_db` | gRPC + NATS | Jenkins/Argo |
| **监控告警中心** | `monitor-svc` | 指标、告警规则、静默、通知路由、巡检 | `monitor_db` | gRPC + NATS | Prometheus/Grafana |
| **作业平台** | `job-svc` | 脚本执行、文件分发、批量任务、定时任务 | `job_db` | gRPC + NATS | SaltStack/Ansible |
| **工单系统** | `ticket-svc` | 工单流程、审批流、表单引擎、SLA | `ticket_db` | gRPC + NATS | Activiti/自研 BPM |
| **审计中心** | `audit-svc` | 操作审计、登录审计、高危操作追溯、合规报表 | `audit_db` + ES | NATS（纯消费） | Elasticsearch |
| **消息通知中心** | `notify-svc` | 钉钉/企微/飞书/邮件/短信/Webhook 统一对接 | `notify_db` | NATS（纯消费） | 各 IM 厂商 SDK |
| **配置中心** | `config-svc` | 应用配置、灰度配置、环境变量、动态下发 | `config_db` | gRPC + 长轮询 | Apollo（可选） |
| **API 网关** | `gateway-svc` | 路由、认证、限流、灰度、协议转换 | 无 | HTTP/WS → gRPC | Consul |
| **BFF 聚合层** | `bff-svc` | 前端聚合、字段裁剪、WebSocket 代理 | 无 | HTTP/WS → gRPC | Gateway |

### 3.2 各模块详细设计

#### 3.2.1 用户中心（auth-svc）

```
auth-svc/
├── cmd/auth/main.go
├── internal/
│   ├── handler/         # gRPC handler
│   ├── service/
│   │   ├── login.go     # 登录：账密 / SSO / OAuth2 / LDAP
│   │   ├── jwt.go       # Token 签发 / 刷新 / 撤销
│   │   ├── user.go      # 用户 CRUD
│   │   ├── org.go       # 组织架构 / 部门树
│   │   └── group.go     # 用户组
│   ├── repository/
│   ├── model/
│   └── middleware/
├── proto/auth.proto
└── migrations/
```

**Proto 接口**：
```protobuf
service AuthService {
  rpc Login(LoginRequest) returns (LoginResponse);
  rpc Logout(LogoutRequest) returns (Empty);
  rpc RefreshToken(RefreshRequest) returns (TokenResponse);
  rpc VerifyToken(VerifyRequest) returns (UserClaims);
  rpc CreateUser(CreateUserRequest) returns (User);

  rpc SyncFromLDAP(SyncRequest) returns (SyncResult);

```

#### 3.2.3 CMDB 资产中心（cmdb-svc）

**CMDB 是平台数据底座**，所有业务模块的资产元数据都来自这里。

```
cmdb-svc/
├── internal/
│   ├── service/
│   │   ├── model.go     # CI 模型定义（主机/数据库/中间件/集群/应用...）
│   │   ├── instance.go  # CI 实例 CRUD
│   │   ├── relation.go  # 关系拓扑（部署/依赖/归属）
│   │   ├── tree.go      # 业务树（部门→业务→集群→应用）
│   │   ├── discovery.go # 自动发现（Agent / SNMP / Cloud API）
│   │   └── history.go   # 变更历史
│   ├── repository/
│   │   ├── mysql/       # 结构化数据
│   │   └── neo4j/       # 关系拓扑（可选，亿级关系用图库）
│   └── ...
└── proto/cmdb.proto
```

**核心特点**：
- **模型可扩展**：通过 JSON Schema 定义任意 CI 类型，无需改代码
- **关系建模**：支持父子、依赖、部署等多维关系，前端拓扑图直接读取
- **变更追溯**：所有 CI 变更记录到审计中心，可回放任意历史时刻状态

```

**与其他模块协作**：

#### 3.2.8 审计中心（audit-svc）

```
audit-svc/
├── internal/
│   ├── consumer/        # 纯消费者（NATS 订阅所有审计事件）
│   ├── service/
│   │   ├── login.go     # 登录审计
│   │   ├── operation.go # 操作审计
│   │   ├── danger.go    # 高危操作识别

│   │   └── search.go    # ES 全文检索

│   │   ├── mysql/       # 元数据
│   │   └── es/          # 全文检索 + 长期归档

**特点**：
- **写多读少**：所有写入走 NATS 异步，业务无感
- **冷热分层**：MySQL 存近 90 天，ES 存全量，归档到对象存储
- **不可篡改**：哈希链 / 区块链存证（合规要求高时）

## 四、平台底座 + 插拔式扩展机制

### 4.1 底座 vs 业务模块边界

| 特性 | 平台底座（5 个） | 业务模块（5+ 个） |
|------|----------------|------------------|
| **稳定性要求** | 极高（影响全平台） | 高（影响单一域） |
| **扩展频率** | 低（接口冻结） | 中（持续迭代） |
| **依赖方向** | 业务 → 底座（单向） | 业务 ↔ 业务（事件解耦） |
| **数据库** | 独立 + 必须高可用 | 独立，按业务量级伸缩 |
| **发布策略** | 严格灰度 + 全链路回归 | 模块独立发布 |
| **典型成员** | auth/rbac/audit/notify/config | cmdb/cicd/monitor/job/ticket |

### 4.2 插拔式接入规范

新业务模块（如成本分析 `cost-svc`、容量管理 `capacity-svc`、AI 运维 `aiops-svc`）按统一规范接入：

```
新模块上线 Checklist：
□ 1. 注册到 Consul，服务名 xxx-svc
□ 2. 实现 HealthCheck gRPC 接口（底座统一探活）
□ 3. 提供 OpenAPI 描述（自动注册到 Gateway）
□ 4. 接入 auth-svc 验证 Token（统一认证）
□ 5. 接入 rbac-svc 鉴权（统一权限）
□ 6. 关键操作发审计事件到 NATS（统一审计）
□ 7. 通知走 notify-svc（统一消息）
□ 8. 配置项托管在 config-svc（统一配置）
□ 9. 提供 Prometheus /metrics 端点
□ 10. 接入 OpenTelemetry 链路追踪
□ 11. 前端打包为 wujie 子应用并注册到主门户
□ 12. 数据库独立 Schema，禁止跨库 JOIN
```

### 4.3 模块发现与动态注册

底座提供 `module-svc`（轻量服务）维护「平台已接入模块」清单：

```protobuf
service ModuleService {
  rpc Register(RegisterRequest) returns (Empty);     // 模块上线注册
  rpc Deregister(DeregisterRequest) returns (Empty);
  rpc List(Empty) returns (ModuleList);              // 前端读取菜单
  rpc Heartbeat(HeartbeatRequest) returns (Empty);
}

message Module {
  string name = 1;             // 服务名
  string display_name = 2;     // 中文名（用户中心 / CMDB...）
  string version = 3;
  string icon = 4;             // 菜单图标
  string entry_url = 5;        // 子应用入口
  repeated string permissions = 6; // 暴露的权限点
  string openapi_url = 7;      // OpenAPI 描述地址
}
```

前端门户启动时拉取 `Module.List`，动态渲染菜单 → 真正实现"插拔即用"。

## 六、服务注册与发现方案

### 6.1 选型决策

| 部署形态 | 推荐方案 | 理由 |
|---------|---------|------|
| 纯 K8s 单集群 | **K8s Service + DNS** | 零运维成本，K8s 原生 |
| 跨 K8s 集群 / 混合云 | **Consul** | WAN Federation 原生支持 |
| Java/Go 混合栈 | Nacos | 阿里生态成熟 |
| 老 etcd 项目 | etcd | 复用基础设施 |

**OpsPlatform 默认采用 Consul + K8s DNS 双模式**，由 `pkg/discovery` 自动检测环境切换。

### 6.2 Consul 注册流程

```go
// pkg/registry/consul.go
package registry

import "github.com/hashicorp/consul/api"

type Registrar struct{ client *api.Client; id string }

func New(consulAddr string) (*Registrar, error) {
    cfg := api.DefaultConfig(); cfg.Address = consulAddr
    cli, err := api.NewClient(cfg)
    return &Registrar{client: cli}, err
}

func (r *Registrar) Register(svc ServiceInfo) error {
    r.id = svc.ID
    return r.client.Agent().ServiceRegister(&api.AgentServiceRegistration{
        ID: svc.ID, Name: svc.Name, Address: svc.IP, Port: svc.Port,
        Tags: svc.Tags, Meta: svc.Meta,
        Check: &api.AgentServiceCheck{
            GRPC:                           fmt.Sprintf("%s:%d", svc.IP, svc.Port),
            Interval:                       "10s",
            Timeout:                        "3s",
            DeregisterCriticalServiceAfter: "30s",
        },
    })
}

func (r *Registrar) Deregister() error {
    return r.client.Agent().ServiceDeregister(r.id)
}
```

### 6.3 服务发现 + 客户端负载均衡

```go
// pkg/discovery/dialer.go
package discovery

import (
    "fmt"
    "google.golang.org/grpc"
)

func Dial(svcName string) (*grpc.ClientConn, error) {
    target := resolveTarget(svcName)
    return grpc.Dial(target,
        grpc.WithInsecure(),
        grpc.WithDefaultServiceConfig(`{
            "loadBalancingPolicy":"round_robin",
            "methodConfig":[{
                "name":[{}],
                "retryPolicy":{
                    "maxAttempts":3,
                    "initialBackoff":"0.1s","maxBackoff":"1s",
                    "backoffMultiplier":2,
                    "retryableStatusCodes":["UNAVAILABLE","DEADLINE_EXCEEDED"]
                }
            }]
        }`),
    )
}

func resolveTarget(svc string) string {
    if isInK8s() {
        // K8s Headless Service + DNS
        return fmt.Sprintf("dns:///%s-headless.ops-platform.svc.cluster.local:50051", svc)
    }
    // Consul Resolver
    return fmt.Sprintf("consul:///%s", svc)
}
```

## 七、服务间通信设计

### 7.1 通信矩阵（核心调用关系）

| 调用方 | 被调用方 | 方式 | 场景 |
|-------|---------|------|------|
| gateway-svc | auth-svc | gRPC | Token 验证 |
| gateway-svc | rbac-svc | gRPC | 权限判定 |
| 所有业务服务 | auth-svc | gRPC | 用户信息查询 |
| 所有业务服务 | rbac-svc | gRPC | 鉴权 |
| 所有业务服务 | NATS → audit-svc | 事件 | 操作审计 |
| 所有业务服务 | NATS → notify-svc | 事件 | 消息通知 |
| cicd-svc | cmdb-svc | gRPC | 拿应用元数据 |
| cicd-svc | ticket-svc | gRPC | 创建发布工单 |
| cicd-svc | NATS → monitor-svc | 事件 | 发布静默告警 |
| job-svc | cmdb-svc | gRPC | 拿目标主机 |
| monitor-svc | cmdb-svc | gRPC | 拿告警主体 |
| ticket-svc | NATS → cicd-svc | 事件 | 工单审批通过触发发布 |

### 7.2 同步通信（gRPC）

适用：**强一致路径**，调用方必须等结果。
- 鉴权、获取连接、读取主数据
- Proto 优先，自动生成多语言客户端

### 7.3 异步通信（NATS JetStream）

适用：**弱一致联动**，调用方不关心结果。
- 审计、通知、跨域联动
- 事件持久化，消费者可重放

```go

### 8.1 网关职责

```

                                              │

|------|------|

### 8.3 BFF 层定位

BFF（Backend For Frontend）解决「前端一次渲染需要 N 个微服务数据」的痛点：

```go
// services/bff-svc/internal/handler/dashboard.go
func (h *DashboardHandler) GetOverview(c *gin.Context) {
    var (
        ciCount    int64
        pipelines  []*pb.Pipeline
        alerts     []*pb.Alert
        jobs       []*pb.Job
        tickets    []*pb.Ticket
    )
    g, ctx := errgroup.WithContext(c.Request.Context())
    g.Go(func() error { return rpc(ctx, h.cmdbCli.Count, &ciCount) })
    g.Go(func() error { return rpc(ctx, h.cicdCli.Recent, &pipelines) })
    g.Go(func() error { return rpc(ctx, h.monitorCli.Firing, &alerts) })
    g.Go(func() error { return rpc(ctx, h.jobCli.Recent, &jobs) })
    g.Go(func() error { return rpc(ctx, h.ticketCli.Pending, &tickets) })
    if err := g.Wait(); err != nil {
        c.JSON(500, gin.H{"error": err.Error()}); return
    }
    c.JSON(200, gin.H{
        "ci_count": ciCount, "pipelines": pipelines,
        "alerts": alerts, "jobs": jobs, "tickets": tickets,
    })
}
```

## 十、数据治理与中间件

### 10.1 分库策略

每个微服务独占 Schema，物理上可共享一组 MySQL（中小规模）或独立实例（大规模）。

```
MySQL Cluster
├── auth_db      (用户、Session)
├── rbac_db      (角色、权限点、绑定)
├── cmdb_db      (CI、关系、模型)
├── cicd_db      (流水线、构建、制品)
├── monitor_db   (告警规则、渠道、静默)
├── job_db       (作业、执行实例)
├── ticket_db    (工单、流程、审批)
├── audit_db     (审计元数据，全量数据在 ES)
├── notify_db    (渠道、模板、发送记录)
└── config_db    (配置项、版本)
```

### 10.2 跨服务数据一致性

| 场景 | 方案 |
|------|------|
| 跨服务查询 | gRPC 调用 + BFF 聚合，禁止跨库 JOIN |
| 跨服务事务 | Saga 模式（事件驱动 + 补偿） |
| 缓存一致 | 数据变更发事件，订阅者主动失效 |
| 强一致需求 | 设计上避免跨服务事务，必要时合并到单服务 |

### 10.3 Redis 用途

```
auth:session:{user_id}           # 会话
auth:token:{token_hash}          # JWT 黑名单
rbac:user_perms:{user_id}        # 权限缓存（TTL 5min）
cmdb:ci:{ci_id}                  # 热点资产缓存
cicd:lock:pipeline:{id}          # 分布式锁
job:queue                        # 待执行作业队列
notify:ratelimit:{channel}       # 通知限流
```

### 10.4 ES 与 Prometheus 边界

- **ES**：审计日志全文检索、CMDB 全文搜索、Loki 日志聚合
- **Prometheus**：所有服务的 `/metrics`、监控告警数据源
- **VictoriaMetrics**：替代 Prometheus 长期存储（≥30 天）

## 十六、面试表达模板

### 16.1 完整答题脚本

> 当面试官问「你怎么设计一个统一运维平台」时，按这 9 步讲：

1. **先抛业务背景**：运维平台天然包含 CMDB、CI/CD、监控、作业、工单、权限、审计等多个业务域，单体后期维护成本极高。

2. **整体架构**：我会做成「**前端统一门户 → API 网关 → 平台底座 → 业务微服务 → 数据中间件**」五层结构。

3. **平台底座**：用户、权限、审计、消息通知、配置 5 个公共能力下沉为底座，所有业务模块复用，避免重复造轮子。

4. **业务模块拆分**：按 DDD 领域划分 8 个核心模块——CMDB 管资产元数据，CI/CD 管发布流程，监控管观测告警，作业管批量执行，工单管审批闭环，每个模块独立数据库 Schema。

5. **服务通信**：强一致路径走 gRPC（鉴权、查主数据），弱一致联动走 NATS 事件（审计、通知、CICD 联动静默）。

6. **服务注册发现**：纯 K8s 用 Service+DNS，跨集群混合云用 Consul，**双模封装**屏蔽差异。

7. **前端**：Vue3 主门户 + wujie 微前端，每个业务团队独立开发独立发版，主门户菜单从 module-svc 动态加载，**真正实现插拔式扩展**。

8. **演进策略**：团队规模 < 5 人时**先做模块化单体**，预留拆分点；5~10 人拆出底座；10~20 人拆出业务；20+ 人引入 Service Mesh 精细治理。**避免为了微服务而微服务**。

9. **加分点八件套**：CMDB 是数据底座、权限中心统一认证授权、工单系统负责审批闭环、CI/CD 负责发布执行、监控平台负责观测告警、作业平台负责批量运维、审计中心记录所有高危操作、消息中心统一对接钉钉/企微/邮件。

### 16.2 关键金句

- 「**CMDB 是核心数据底座，所有业务模块的资产元数据都来自 CMDB，CMDB 的稳定性等于平台稳定性。**」
- 「**审计、通知、配置都是平台底座，业务方一行代码发事件即可，不关心实现。**」
- 「**新模块按统一接入规范上线，前端无需改菜单代码，体现真正的插拔式扩展。**」
- 「**微服务不是银弹，团队规模和复杂度匹配才上，否则模块化单体也是好选择。**」

### D.4 技术难点与解决方案（面试必问追问）

#### 难点 1：跨服务数据一致性

> **问题**：CI/CD 发布成功后需要同时更新 CMDB 的版本字段 + 创建审计记录 + 发通知——跨 3 个服务。
>
> **方案**：不做分布式事务。我采用**事件驱动 + Saga 补偿**——
> 1. cicd-svc 发布成功后，发 NATS 事件 `cicd.deploy.done`
> 2. cmdb-svc 订阅此事件，更新 CI 版本字段
> 3. audit-svc 订阅此事件，写审计日志
> 4. notify-svc 订阅此事件，发钉钉通知
> 5. 如果 cmdb 更新失败，有重试 + 死信队列 + 告警人工介入
>
> **效果**：彻底解耦，各模块独立容错，通知/审计不影响主链路。

#### 难点 2：CMDB 模型灵活性 vs 查询性能

> **问题**：运维场景资源类型多变（主机/数据库/中间件/容器/自定义），如果每种类型建一张表，后续扩展极其痛苦。
>
> **方案**：我设计了 **动态模型引擎**——
> - 模型定义：一张 `ci_models` 表存 JSON Schema（定义有哪些字段、类型、校验规则）
> - 实例存储：一张 `ci_instances` 表 + 一张 `ci_attributes` 宽表（EAV 模型，或 MySQL 8 JSON 列）
> - 查询加速：对高频查询字段建 **索引表**（如 hostname、ip），写入时同步维护
> - 关系：独立 `ci_relations` 表，支持任意拓扑关系（亿级关系量级时引入 Neo4j）
>
> **效果**：新增资源类型前端表单配置 → JSON Schema → 零代码上线。

#### 难点 3：gRPC 长连接负载不均

> **问题**：K8s 环境下用 ClusterIP Service，gRPC 长连接一直打到同一个 Pod，扩容无效。
>
> **方案**：
> 1. 改用 **Headless Service**（clusterIP: None），让客户端拿到所有 Pod IP
> 2. gRPC Dial 时配置 `dns:///` 前缀 + `round_robin` 负载策略
> 3. 客户端定时 re-resolve DNS（gRPC 内置 30s 刷新）
>
> **效果**：扩 Pod 后 30s 内自动均衡，QPS 线性增长。

#### 难点 4：审计日志海量写入

> **问题**：平台日活 500+ 用户，每天 50 万条审计事件，同步写 MySQL 会拖慢业务。
>
> **方案**：
> 1. 业务方异步发 NATS 事件（业务零延迟感知）
> 2. audit-svc 批量消费（每 100 条或 1s 一批）
> 3. 近 90 天数据在 MySQL（查询快），全量在 ES（全文检索），180 天以上归档对象存储
>
> **效果**：审计链路对业务**零耦合零延迟**，存储成本下降 70%。

#### 难点 5：微前端子应用通信与状态同步

> **问题**：主门户和子应用是独立工程，用户信息、集群切换、主题切换需要同步。
>
> **方案**：使用 wujie props 注入 + 事件总线——
> 1. 主门户通过 `props` 传递响应式 user/token/cluster 给子应用
> 2. 子应用通过 `window.$wujie.bus.$emit` 向主门户发消息
> 3. 共享 NPM 包（@ops/request）内置 axios 拦截器，自动注入 Token + ClusterID
>
> **效果**：子应用完全独立开发运行，嵌入主门户时**零适配成本**。

### D.6 面试追问及应对（Q&A 模拟）

#### Q：为什么选 Go 不选 Java？

> Go 在云原生领域生态优势明显（K8s/Docker/Prometheus/Consul 全是 Go 写的），编译为单二进制部署简单，协程天然适合高并发 IO（WebSocket 终端、批量作业），内存占用低（单服务 ~50MB vs Spring 动辄 500MB）。团队也以 Go 为主。

#### Q：为什么选 Consul 不选 Nacos？

> 1. 我们有跨 IDC 部署需求，Consul 原生 WAN Federation 支持多数据中心 Gossip
> 2. Go 官方 SDK 成熟度高于 Nacos 社区 Go SDK
> 3. 自带 Service Mesh（Connect），后续演进成本低
> 4. Nacos 更适合 Java / Spring Cloud 生态

#### Q：为什么选 NATS 不选 Kafka？

> 1. 平台事件量级 ~50 万/天（对 Kafka 来说太小，运维成本不匹配）
> 2. NATS 单二进制部署极简，Go 生态原生
> 3. JetStream 支持持久化、重放、消费者组，满足需求
> 4. 延迟低（µs 级），适合审计/通知这种轻量事件
> 5. 未来数据量增长到亿级再考虑 Kafka

#### Q：为什么选 wujie 不选 qiankun？

> 1. qiankun 基于 JS 沙箱 + Proxy，存在 CSS 隔离不完美的问题
> 2. wujie 基于 WebComponent + iframe，CSS/JS 天然完美隔离
> 3. Vue3 + Vite 适配最好（qiankun 对 Vite 需额外 patch）
> 4. wujie alive 模式支持 keep-alive，切换子应用不销毁状态

#### Q：微服务最大的坑是什么？怎么解决的？

> **最大的坑是过早微服务化**。项目初期我们就想一步到位拆 12 个服务，结果前两个月开发速度非常慢——Proto 变更频繁、联调成本高、本地起一堆服务内存爆炸。
>
> **我的调整**：退回模块化单体，先按 `internal/auth`、`internal/cmdb` 分包跑 3 个月，业务稳定后再逐步拆。这个教训让我深刻理解了「**微服务不是银弹，团队规模和复杂度匹配才上**」。

#### Q：你怎么保证各个微服务接口兼容性？

> 1. Proto 定义集中管理（独立目录 `api/`），打 Tag 版本化
> 2. 字段变更**只增不删**（删除字段保留 `reserved`），保证滚动升级期间新老版本兼容
> 3. 重大变更升 package 版本（`auth.v1` → `auth.v2`），双版本并行过渡
> 4. CI 流水线增加 `buf breaking` 检测，自动拦截不兼容变更

#### Q：CMDB 怎么保证数据准确？

> 三管齐下：
> 1. **自动发现**：Agent 定时上报 + Cloud API 定时同步 → CMDB 自动入库
> 2. **变更联动**：CI/CD 发布成功后自动更新 CMDB 的版本/镜像字段
> 3. **人工兜底**：定期对比巡检（CMDB vs 实际环境），差异项推送工单确认
>
> 准确率从 40% 提升到 95%+。

#### Q：生产发布怎么做灰度？

> 1. **网关灰度**：Gateway 按 Header（X-Gray: true）/ 用户 ID 哈希将流量路由到新版本
> 2. **K8s 灰度**：Deployment + Service 双版本并存，VirtualService 按权重分流
> 3. **发布审批**：生产发布必须走工单（ticket-svc），技术负责人 + SRE 二级审批
> 4. **自动回滚**：发布后 5min 内错误率 >1% 自动触发回滚 + 通知

#### Q：如果让你重新设计，会有什么不同？

> 1. **一开始就用 buf 管理 Proto**，而不是手动 protoc（buf 的 breaking 检测很香）
> 2. **更早引入 BFF 层**，避免前端和各个微服务直连
> 3. **CMDB 的关系拓扑从一开始就用 Neo4j**，MySQL 建模关系拓扑太勉强
> 4. **日志一开始就接 Loki**，而不是先 EFK 后迁移
